# Сопоставление колонок при импорте

Спецификация для этапа импорта: какая колонка каждого листа во что
превращается. Составлена по рабочему файлу заказчика, заполненность колонок
указана по факту — она говорит, на что можно опираться, а что в файле почти
пустое.

Документ не зависит от того, какая кодовая база станет основой: сопоставление
одинаково для любой.

## Как читать таблицы

Колонка «Заполнено» — сколько содержательных строк реально имеют значение.
Колонка «Куда» — поле модели или «—», если колонка не переносится, с
объяснением почему.

## 1. Письма ЭДО (50 записей)

| Колонка | Заполнено | Куда |
| --- | --- | --- |
| № | — | — (нумерация строк листа, не номер письма) |
| Номер письма | 50 | `Letter.number` |
| Дата письма | 50 | `Letter.letterDate` |
| Тема | 50 | `Letter.subject` |
| Ссылка на письмо | 50 | `Letter.externalUrl` |
| Тип | 50 | `Letter.direction`: «Входящее» → `INCOMING`, «Исходящее» → `OUTGOING` |
| Контрагент | 50 | `Letter.counterpartyId` через справочник написаний |
| Срок исполнения | 17 | `Letter.dueDate` |
| Просроченные | 35 | **не переносится напрямую**, см. ниже |
| Ответ реквизиты | 17 | `Letter.responseRequisites` |
| Статус | 49 | `Letter.status` по словарю ниже |
| Задача в Jira | 1 | `Letter.jiraKey` |
| Комментарий | 12 | `Note` с датой письма как датой события |

### Колонка «Просроченные» — смесь двух разных вещей

Разбор показал не то, что ожидалось. Из 35 значений 32 — это «исполнено», и
только 3 — собственно просрочка («просрочка 49 дн.», «просрочка 4 дн.»,
«просрочка 5 дн.»).

Хуже: **19 записей несут отметку без срока исполнения**. Там просрочку нельзя
вычислить в принципе — не от чего считать.

Правило разбора:

- «исполнено» → это отметка исполнения, а не просрочки. Переносится в статус
  письма (`ANSWERED`, `SIGNED` или `NOTED` — по колонке «Статус»), и в
  отдельное поле не кладётся.
- «просрочка N дн.» → не переносится: система считает просрочку сама от срока
  и текущей даты.
- Отметка при пустом сроке → в лог импорта строкой «отметка есть, срока нет»,
  чтобы человек при желании внёс срок.

Прежняя формулировка в разборе файла («просрочка записана текстом и
устаревает») была верна лишь для трёх записей из пятидесяти. Содержательно
вывод тот же — хранить просрочку полем не нужно, — но обоснование теперь
точное.

### Словарь статусов письма

| В файле | В системе |
| --- | --- |
| Дан ответ | `ANSWERED` |
| Подписано | `SIGNED` |
| Принято к сведению | `NOTED` |
| в работе | `IN_PROGRESS` |
| ответ в работе | `IN_PROGRESS` |
| Ответ на согласовании | `UNDER_REVIEW` |
| «На согласовании у <фамилия>» | `UNDER_REVIEW` + `Note` с текстом как есть |

Последняя строка — общий приём: когда в статус вписана фамилия или дата,
статус берётся по смыслу, а исходный текст целиком уходит в ленту записей.
Терять его нельзя.

## 2. Реестры задач (три листа: внутренние 20, внешние 2, производственные 3)

Структура листов почти одинаковая, различается одной колонкой.

| Колонка | Куда |
| --- | --- |
| Дата создания | `Task.createdAt` |
| Письмо, задача, поручение | `Task.title`; длинный текст — первая строка в `title`, остальное в `description` |
| Ответственный / Ответственный от ДИТ | `TaskAssignee`, см. ниже |
| Внешний ответственный (только внешние задачи) | `Task.externalAssignee` |
| Плановый срок / Срок | `Task.plannedEnd` |
| Статус | **не статус**, см. ниже |
| Результат (ссылки на ЭДО, комментарии) | `Note` |

Лист задаёт трек: внутренние → «Официальный», внешние → «Внешние
взаимодействия», производственные → «Производственный». Названия треков
уточняются у заказчика, но разделение по листам сохраняется.

### Колонка «Статус» в реестрах задач

Это не состояние, а хроника. Реальные значения: «05.05.2026 драфт письма
загружен в ЭДО / 06.05.2026 на согласовании», «На согласовании с
29.04.2026», «Выполнено 20.05.2026».

Правило разбора:

1. Текст разбивается на записи по датам в начале фрагмента.
2. Каждая запись становится `Note` с распознанной датой в `occurredOn`.
3. Если во фрагменте есть слово «выполнено», статус задачи ставится в
   категорию `DONE`, дата из фрагмента — в `actualEnd`.
4. Фрагмент, из которого дату вытащить не удалось, сохраняется одной записью с
   датой создания задачи.
5. Каждая распознанная запись показывается человеку на подтверждение.

Пункты 4 и 5 не оптимизация, а страховка: эвристика будет ошибаться, и
потерять хронику хуже, чем оставить её одной строкой.

### Ответственные

Одна ячейка часто содержит несколько человек: две фамилии через запятую или
разделение зон ответственности текстом («первый — техническая фактура, вторая
— переписка»).

Правило: ячейка режется по запятой, каждый фрагмент ищется в справочнике
сотрудников. Первый найденный помечается `isPrimary`. Если во фрагменте есть
пояснение помимо фамилии, вся ячейка целиком дополнительно сохраняется в
`Note` — пояснение о разделении зон ценнее, чем аккуратный список.

## 3. Регламенты информационного взаимодействия (9 документов)

Строка листа — один документ вида `REGULATION` на одного контрагента.

| Колонка | Заполнено | Куда |
| --- | --- | --- |
| РСО | 9 | `Document.counterpartyId` |
| Статус ДИТ | 9 | `Document.originatorStage` — **стадия, не подпись** |
| Статус подписания ДИТ | 9 | `DocumentParty` для ДИТ |
| Статус подписания РСО | 9 | `DocumentParty` для контрагента |
| Статус подписания ДЖКХ | 9 | `DocumentParty` для ДЖКХ |
| Актуальный статус | 5 | `Document.stateNote` |
| Актуальные задачи | 9 | `Task`, связанная с документом через `DocumentTask` |
| Ответственный | 9 | `DocumentParty.ownerId` соответствующей стороны |
| Письмо из ДИТ, которым отправлено | 8 | `DocumentParty.basisLetterId` (исходящее) |
| Ссылка на ЭДО | 9 | `Letter.externalUrl` письма-основания |
| Письмо с ответом от РСО или ДЖКХ | 7 | `DocumentParty.basisLetterId` (входящее) |
| Срок интеграции, факт | 7 | `Document.integrationDueDate` |
| Статус согласования | 8 | `Document.approvalNote` |
| Итоговый статус подписания | 1 | `Document.finalStatusText` |

**Главная ловушка этого листа.** «Статус ДИТ» и «Статус подписания ДИТ» — две
разные колонки, и из первой нельзя вывести вторую: при одной и той же стадии
«Заслан» подпись стоит «Подписан» в пяти строках и «Нет» в трёх. Разбор обеих
как сторон даёт дубль стороны ДИТ с противоречащими статусами.

Правило: сторону создаёт только колонка со словом «подписания». «Статус ДИТ»
идёт в `originatorStage`.

Заметим, что содержательной информации в этой колонке почти нет — 8 строк
«Заслан» и 1 «в работе», — так что не переносить её тоже допустимо. Но
«почти нет» и «нет» это разные вещи: одна строка отличается.

**«Статус согласования» отстаёт от матрицы.** Текст в этой колонке — хроника
переписки, и он не синхронизирован со статусами сторон. У строки «ГУП
Мосводосток» матрица даёт ДЖКХ = «Подписан», а текст говорит «На подписании в
ДЖКХ». Состояние документа берём из матрицы подписей, текст кладём в
`approvalNote` как есть и не пытаемся их согласовать при импорте.

**ДЖКХ — не контрагент этих документов.** В колонке «РСО» девять разных
организаций, и ДЖКХ среди них не встречается ни разу: это третья
подписывающая сторона, одна и та же на всех девяти строках. Отдельный признак
«третья сторона» на этих данных хранить нечего — он был бы константой; если
понадобится отличать согласующее ведомство от подписанта по договору, это роль
стороны, а не сравнение с контрагентом документа.

Кого ждут документы на текущих данных: ДЖКХ не подписал в 5 строках из 9, РСО
— в 4; при этом единственным блокером ДЖКХ оказывается один раз (ПАО Россети,
ДИТ и РСО подписали), а РСО единственным блокером — ни разу. Ответ на вопрос
«кого ждём» даёт перечисление имён неподписавших внешних сторон, а не категория.

### Словарь статусов стороны

| В файле | В системе |
| --- | --- |
| Нет | `NOT_SENT` |
| Согласован | `AGREED` |
| Подписан | `SIGNED` |
| Не согласован РСО | `REFUSED`, причина из итоговой колонки |

Значения «Заслан» и «Отправлен» в этот словарь не входят: они приходят из
колонки стадии, а не из колонок подписания.

## 4. ДС к NDA (9 документов)

Строка — документ вида `NDA_ANNEX`. Лист устроен иначе, чем регламенты.

| Колонка | Заполнено | Куда |
| --- | --- | --- |
| РСО | 9 | `Document.counterpartyId` |
| Направлен из ДИТ в РСО | 9 | `DocumentParty.sentAt` + реквизиты письма в `basisLetter` |
| Ответ от РСО | 9 | `DocumentParty.respondedAt` + реквизиты письма |
| Статус согласования | 9 | `DocumentParty` контрагента по словарю выше |
| Статус ДИТ | 9 | `Document.originatorStage` |
| Итоговый статус подписания | 9 | `Document.finalStatusText` + `stateOverride`, см. ниже |
| Задача администратору | 1 | `Task`, связанная через `DocumentTask` |

**Вторая ловушка.** Колонок «Статус подписания <сторона>» здесь нет вообще, а
отказ записан только в итоговой колонке: «Отказали в подписании, сославшись на
секретность» — две строки из девяти.

Правило: итоговая колонка разбирается и в текст (`finalStatusText`), и, если в
ней зафиксирован исход, в `stateOverride` с причиной. Вывод состояния из
сторон на этих строках дал бы «черновик» при фактическом отказе.

Формулировка «Подписан, экземпляр передан в РСО» переносится текстом целиком:
факт передачи экземпляра в статусах сторон не выражается.

## 5. График интеграций с РСО (9 контрагентов)

Строка — контрагент, колонка — этап. Каждая пара превращается в
`CounterpartyMilestone`.

| Колонка | Заполнено | Этап (`stage`) |
| --- | --- | --- |
| Регламент информационного взаимодействия (дата отправки) | 9 | Регламент отправлен |
| Дата подписания регламента | 9 | Регламент подписан |
| Дата готовности ИС РСО к отладке | 0 | Готовность системы контрагента |
| Дата интеграции в dev среде | 5 | Интеграция в dev |
| Открытие интеграции в тестовой среде | 5 | Открытие в тестовой среде |

Дата из колонки идёт в `plannedDate`, если она в будущем, и в `actualDate`,
если в прошлом. Различить план и факт по самому листу нельзя — колонки
названы просто «дата», — поэтому при импорте это показывается человеку.

Этап «Готовность системы контрагента» не заполнен ни у кого. Колонку заводим,
но в интерфейсе по умолчанию скрываем: пустой столбец на девять строк только
мешает.

## 6. Отчёт руководству (1 проект, блоки по трекам)

Лист устроен вертикально: шапка проекта в первой строке, дальше блоки по
трекам.

| Колонка | Заполнено | Куда |
| --- | --- | --- |
| Название проекта | 1 | сопоставляется с существующим проектом |
| Руководитель проекта | 1 | `StatusReport.projectLead` |
| Наличие контракта (статус) | 1 | `StatusReport.contractStatus` |
| Релиз (тема, дата) | 1 | `StatusReport.nextRelease` |
| План развития 2026–2028 | 1 | `StatusReport.developmentPlan` |
| Выполненные работы за 2 недели | 13 | `ReportSection.doneText`, по блоку на трек |
| Ответственны за заполнение | 12 | `ReportSection.responsible` |
| Текущие блокеры | 1 | `ReportSection.blockersText` |
| Предлагаемые решения | 1 | `ReportSection.solutionsText` |
| Запланированные работы на следующие 2 недели | 4 | `ReportSection.plannedText` |

Импортируется как один отчёт в состоянии `SUBMITTED`: это уже ушедший
руководству документ, и правке он не подлежит.

Блоки в колонке «Выполненные работы» пронумерованы и озаглавлены треками
(«Официальный трек», «Юридический трек», «Анализ территории», «Разработка») —
из этих заголовков и берётся набор треков проекта.

## 7. Чего импорт не делает

- **Не создаёт письма из реквизитов в реестрах документов.** В колонках
  регламентов номер письма записан текстом вместе с датой и ссылкой. Импорт
  сохраняет текст и ссылку, а связывание с письмом из реестра переписки
  предлагает человеку: сопоставление по номеру ненадёжно, номера в реестрах
  записаны по-разному.
- **Не разбирает вложенность задач.** Подзадач в листах нет, иерархию строит
  человек после импорта.
- **Не угадывает зависимости между задачами.** В файле их нет вообще.
- **Не сводит дубли задач между листами.** Одна работа может быть упомянута и
  во внутренних задачах, и в реестре регламентов; решает человек.

## 8. Про связь с Jira

Колонка «Задача в Jira» заполнена **в 1 записи из 50**, и это ссылка на
self-hosted Jira, а не на облако Atlassian.

Отсюда две поправки к более раннему обоснованию:

- Утверждение «в файле уже есть колонка с Jira, значит так это и работает
  сейчас» было преувеличением. Колонка есть, практики связывания нет.
- Решение хранить ключ задачи остаётся, но опирается оно на слова заказчика
  («команда пользуется Jira»), а не на данные файла.

Для интеграции это означает: экземпляр свой, поэтому доступ и аутентификация
настраиваются отдельно, а не берутся готовыми как для облака. Уточнить у
заказчика до этапа интеграции.
