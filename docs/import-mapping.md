# Сопоставление колонок при импорте

Какая колонка каждого листа во что превращается. Составлено по рабочему файлу
заказчика; колонка «Заполнено» — сколько содержательных строк реально имеют
значение, она говорит, на что можно опираться, а что в файле почти пустое.

Имена полей — из `prisma/schema.prisma`. Списки синонимов заголовков, по
которым колонка узнаётся в файле, лежат в `src/lib/excel/columns.ts`: шапка
ищется в первых десяти строках листа, а заголовок сопоставляется сначала точно,
потом по вхождению слова.

## 1. Письма ЭДО (50 записей)

| Колонка | Заполнено | Куда |
| --- | --- | --- |
| № | — | — (нумерация строк листа, не номер письма) |
| Номер письма | 50 | `Letter.number` |
| Дата письма | 50 | `Letter.date` |
| Тема | 50 | `Letter.subject` |
| Ссылка на письмо | 50 | `Letter.url` |
| Тип | 50 | `Letter.direction`: «Входящее» → `INCOMING`, «Исходящее» → `OUTGOING` |
| Контрагент | 50 | `Letter.counterpartyId` через справочник написаний |
| Срок исполнения | 17 | `Letter.dueDate` |
| Просроченные | 35 | не переносится, см. ниже |
| Ответ реквизиты | 17 | `Letter.responseRef` |
| Статус | 49 | `Letter.status` по словарю ниже; нераспознанный текст целиком — в `Letter.statusNote` |
| Задача в Jira | 1 | `Letter.externalTaskKey` |
| Комментарий | 12 | `Letter.comment` |

Письмо узнаётся по паре `(номер, направление)`: повторный импорт того же файла
обновляет запись, а не создаёт вторую. Один и тот же номер встречается и во
входящем, и в исходящем, поэтому направление входит в ключ.

Если в ячейке контрагента записано несколько организаций, в справочник идёт
первая, а исходный текст целиком дописывается в комментарий строкой
«Адресаты: …». Молча выбрасывать вторую организацию нельзя, заводить
несуществующего контрагента «А и Б» — тем более.

### Колонка «Просроченные» — смесь двух разных вещей

Из 35 значений 32 — это «исполнено», и только 3 — собственно просрочка
(«просрочка 49 дн.»). Хуже: **19 записей несут отметку без срока исполнения**,
там просрочку нельзя вычислить в принципе.

Поэтому колонка не импортируется вообще: просрочка считается от `dueDate` и
текущей даты, а отметка исполнения дублирует колонку «Статус», по которой
статус письма и определяется.

### Словарь статусов письма

| В файле | В системе |
| --- | --- |
| Дан ответ | `ANSWERED` |
| Подписано | `SIGNED` |
| Принято к сведению | `NOTED` |
| в работе, ответ в работе | `IN_PROGRESS` |
| Ответ на согласовании | `UNDER_REVIEW` |
| «На согласовании у <фамилия>» | `UNDER_REVIEW`, исходный текст в `Letter.statusNote` |

Последняя строка — общий приём: когда в статус вписана фамилия или дата,
статус берётся по смыслу, а исходный текст сохраняется целиком. Терять его
нельзя.

## 2. Реестры задач (три листа: внутренние 20, внешние 2, производственные 3)

| Колонка | Куда |
| --- | --- |
| Дата создания | `Task.startDate` |
| Письмо, задача, поручение | `Task.title`, длинный хвост — в `Task.description` |
| Ответственный / Ответственный от ДИТ | `Task.assigneeId`, см. ниже |
| Внешний ответственный (только внешние задачи) | `Task.externalAssignee` |
| Плановый срок / Срок | `Task.dueDate` |
| Статус | **не статус**, см. ниже |
| Результат (ссылки на ЭДО, комментарии) | `Task.resultLink` |
| Готовность, % | `Task.progress`; доля 0,5 читается как 50 % |

Лист задаёт трек (`Task.track`): внутренние → `INTERNAL`, внешние →
`EXTERNAL`, производственные → `PRODUCTION`. Строки вида «Итого» и «Всего»
пропускаются: это подвал таблицы, а не задача.

### Колонка «Статус» в реестрах задач

Это не состояние, а хроника: «05.05.2026 драфт письма загружен в ЭДО /
06.05.2026 на согласовании», «Выполнено 20.05.2026».

Правило разбора (`src/lib/excel/chronicle.ts`):

1. Текст делится на строки, в каждой ищется дата в начале или в конце.
2. Каждый фрагмент становится `Note` с распознанной датой в `occurredOn`.
3. Если фрагмент начинается со слова «выполнено», задача закрывается, дата из
   фрагмента идёт в `Task.completedAt`.
4. Исходный текст колонки целиком сохраняется в `Task.progressNote` — страховка
   на случай, если разбор ошибся.
5. Повторный импорт не дублирует записи: сравнение идёт по тексту.

### Ответственные

Одна ячейка часто содержит несколько человек: две фамилии через запятую или
разделение зон ответственности текстом («первая — техническая фактура, вторая
— переписка»).

Ответственным становится первый фрагмент, остальное сохраняется: пояснение о
разделении зон ценнее аккуратного списка. Нескольких ответственных у задачи
модель пока не держит, см. [docs/data-model.md](data-model.md).

## 3. Регламенты информационного взаимодействия (9 документов)

Строка листа — один документ вида `REGULATION` на одного контрагента.

| Колонка | Заполнено | Куда |
| --- | --- | --- |
| РСО | 9 | `Document.counterpartyId` |
| Статус ДИТ | 9 | не переносится: это стадия работы, а не подпись |
| Статус подписания ДИТ | 9 | `DocumentSignature` стороны «ДИТ» |
| Статус подписания РСО | 9 | `DocumentSignature` стороны «РСО» |
| Статус подписания ДЖКХ | 9 | `DocumentSignature` стороны «ДЖКХ» |
| Актуальный статус | 5 | `Document.statusNote` |
| Актуальные задачи | 9 | `Document.nextAction` |
| Ответственный | 9 | `Document.ownerId` |
| Письмо из ДИТ, которым отправлено | 8 | `Document.outgoingLetterId`, если письмо удалось связать |
| Ссылка на ЭДО | 9 | реквизиты письма-основания |
| Письмо с ответом от РСО или ДЖКХ | 7 | `Document.incomingLetterId` |
| Срок интеграции, факт | 7 | `Document.dueDate` |
| Статус согласования | 8 | хроника с датами → `Note`, недатированный текст → `Document.statusNote` |
| Итоговый статус подписания | 1 | `Document.statusNote`, и отказ перебивает вывод из сторон |

**Главная ловушка этого листа.** «Статус ДИТ» и «Статус подписания ДИТ» — две
разные колонки, и они расходятся на всех девяти строках: «Заслан» при «Нет».
Разбор обеих как сторон даёт дубль стороны ДИТ с противоречащими статусами.

Правило: когда на листе есть колонки со словом «подписания», стороны берутся
только из них, а «Статус ДИТ» игнорируется.

### Словарь статусов стороны

| В файле | В системе |
| --- | --- |
| Нет, Не подписан, в работе, Заслан, Отправлен, На рассмотрении | `PENDING` |
| Согласован, Подписан | `SIGNED` |
| Не согласован РСО | `DECLINED` |
| Не требуется | `NOT_REQUIRED` |

Значение, которого в словаре нет, не выбрасывается: оно сохраняется текстом в
`DocumentSignature.note`, а статус стороны остаётся `PENDING`.

## 4. ДС к NDA (9 документов)

Строка — документ вида `NDA_ANNEX`. Лист устроен иначе, чем регламенты.

| Колонка | Заполнено | Куда |
| --- | --- | --- |
| РСО | 9 | `Document.counterpartyId` |
| Направлен из ДИТ в РСО | 9 | реквизиты исходящего письма |
| Ответ от РСО | 9 | реквизиты входящего письма |
| Статус согласования | 9 | `DocumentSignature` стороны-контрагента, см. ниже |
| Статус ДИТ | 9 | `DocumentSignature` стороны «ДИТ» |
| Итоговый статус подписания | 9 | `Document.statusNote` и явный исход |
| Задача администратору | 1 | `Document.nextAction` |

**Вторая ловушка.** Колонок «Статус подписания <сторона>» здесь нет вообще.
Статус контрагента записан в колонке «Статус согласования» («Согласован»,
«Подписан», «Не согласован РСО»), а отказ — ещё и в итоговой колонке:
«Отказали в подписании, сославшись на секретность» — две строки из девяти.

Два правила отсюда:

- Если колонок со словом «подписания» на листе нет, стороной становится
  контрагент строки, а его статус берётся из «Статуса согласования». В реестре
  регламентов та же колонка содержит свободный текст с датами, поэтому решает
  не заголовок, а значение: короткая ячейка со словом из словаря — статус,
  всё остальное — хроника.
- Итоговая колонка авторитетнее вывода из сторон. Отказ в ней ставит документу
  `DECLINED`, даже если отдельные стороны успели подписать.

Формулировка «Подписан, экземпляр передан в РСО» переносится текстом целиком:
факт передачи экземпляра в статусах сторон не выражается.

## 5. График интеграций с РСО (9 контрагентов)

Строка — контрагент, колонка — этап; каждая пара соответствует
`CounterpartyMilestone`.

| Колонка | Заполнено | Этап |
| --- | --- | --- |
| Регламент информационного взаимодействия (дата отправки) | 9 | Регламент отправлен |
| Дата подписания регламента | 9 | Регламент подписан |
| Дата готовности ИС РСО к отладке | 0 | Готовность системы контрагента |
| Дата интеграции в dev среде | 5 | Интеграция в dev |
| Открытие интеграции в тестовой среде | 5 | Открытие в тестовой среде |

**Этот лист пока не импортируется:** таблица в модели есть, разбора и экрана
под неё нет. Различить план и факт по листу нельзя — колонки названы просто
«дата», — поэтому при импорте это придётся показывать человеку.

## 6. Отчёт руководству

Лист устроен вертикально: шапка проекта, дальше блоки по трекам
(«Официальный», «Юридический», «Анализ территории», «Разработка») с
выполненными работами, блокерами, решениями и планами на следующий период.

**Этот лист тоже не импортируется.** `WeeklyReport` собирается системой за
выбранный период из закрытых задач, подписанных документов, просрочек и
отказов, дописывается руками и замораживается при отправке. Переносить один
уже ушедший руководству отчёт ради истории смысла мало.

## 7. Чего импорт не делает

- **Не создаёт письма из реквизитов в реестрах документов.** В колонках
  регламентов номер письма записан текстом вместе с датой и ссылкой; связывание
  с письмом из реестра переписки надёжно только по совпадению номера.
- **Не разбирает вложенность задач.** Подзадач в листах нет, иерархию строит
  человек после импорта.
- **Не сводит дубли задач между листами.** Одна работа может быть упомянута и
  во внутренних задачах, и в реестре регламентов; решает человек.
- **Не угадывает зависимости между задачами.** В файле их нет вообще.

## 8. Про связь с Jira

Колонка «Задача в Jira» заполнена **в 1 записи из 50**, и это ссылка на
self-hosted Jira, а не на облако Atlassian. Колонка есть, практики связывания
нет: решение хранить ключ задачи опирается на слова заказчика о том, что
команда работает в Jira, а не на данные файла.

Для интеграции это означает, что доступ и аутентификация настраиваются
отдельно, а не берутся готовыми как для облака. Уточнить у заказчика до этапа
интеграции.
