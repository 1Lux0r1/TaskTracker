# Архитектура TaskTracker

Документ фиксирует стек, границы системы и принятые по умолчанию решения —
в том виде, в каком они реализованы в этом репозитории. Разбор рабочего файла
заказчика, который задаёт требования, — в
[docs/excel-analysis.md](excel-analysis.md).

## 1. Что мы строим

Система ведения проекта, которая заменяет набор рабочих таблиц Excel, живущих
рядом с Jira: реестр переписки ЭДО, реестры задач по трекам, матрицы
подписания юридически значимых документов, график интеграций с организациями и
отчёт руководству.

Следствия для архитектуры:

- Система ведёт **три разных вида записей**: работу (задачи), переписку
  (письма) и документы со сторонами подписания. Это не одна сущность с разными
  метками, у каждой свой жизненный цикл и свои реквизиты.
- Реестровое представление — представление первого класса. Люди пришли из
  таблиц и будут работать так же.
- Импорт существующего файла и выгрузка любого реестра в Excel — часть базовой
  функциональности. Выгрузка остаётся навсегда: отчётность наружу идёт в Excel.
- Хроника важнее статуса. В исходных таблицах колонка «Статус» содержит ленту
  событий с датами, и эту ленту надо сохранить как ленту.
- Отчёт руководству — замораживаемый снимок, а не живая выборка.
- Производственный трек остаётся в Jira. Система хранит ключ задачи, а своими
  задачами ведёт официальный и юридический треки, которых в Jira нет.

## 2. Стек

| Слой | Выбор | Почему именно так |
| --- | --- | --- |
| Язык | TypeScript (strict) | Один язык на фронте и бэке, общие типы модели данных |
| Фреймворк | Next.js 16, App Router, React 19 | Фулстек в одном деплое, серверные компоненты для тяжёлых таблиц |
| Обмен с сервером | Server Actions | Формы вызывают серверные функции напрямую: отдельный слой API при одном клиенте не окупается |
| БД | SQLite через драйвер-адаптер Prisma | Запуск без внешней БД; объёмы это позволяют, переезд на PostgreSQL — смена провайдера и адаптера |
| ORM | Prisma 7 | Версионированные миграции, схема как единый источник правды по модели |
| UI | Tailwind CSS 4 | Утилиты без навязанной темы, компоненты свои |
| Excel | ExcelJS | Чтение исходного файла и выгрузка реестров в привычном виде |
| Валидация | Zod 4 | Одна схема на форму и на серверное действие |
| Тесты | Vitest | Юнит на разбор файла и доменные правила |

### Чего сознательно нет

- **Аутентификации и ролей.** До реальной эксплуатации это первое, что нужно
  добавить: в системе будет служебная переписка. Сейчас вход не спрашивается.
- Отдельного бэкенд-сервиса и микросервисов — при одной команде это лишняя
  граница.
- Realtime через WebSocket — начинаем с перезагрузки данных после действия.
- Диаграммы Ганта, учёта времени, вложений, уведомлений о сроках.
- Интеграции с ЭДО и Jira: данные заводятся вручную или импортом.

## 3. Масштаб

Старт: один проект, три человека.

Требования к производительности снимаются почти полностью. В исходном файле
50 писем и около 25 задач — объём, на котором тормозит только неудачно
написанный запрос. Индексы в схеме есть, но закладывать под них архитектурные
компромиссы не нужно.

Зато поиск нужен сразу, и не из-за объёма, а из-за формата: номер письма вида
`64-01-16906/26` человек помнит частями, и найти его перебором глазами нельзя
даже в пятидесяти строках. По той же причине отдельный поисковый движок не
нужен — см. [docs/search-and-analytics.md](search-and-analytics.md).

## 4. Границы и структура кода

```
src/app/                  маршруты: реестры, карточки, аналитика, календарь
  actions/                серверные действия — валидация входа и вызов домена
  api/export/             выгрузка реестров в xlsx
src/components/           формы и таблицы
src/lib/
  domain.ts               словари статусов и правила: вывод статуса документа,
                          просрочка, признак закрытого письма
  validation.ts           zod-схемы форм, общие для клиента и сервера
  reports.ts              сборка черновика отчёта за период
  search.ts               подготовка поисковой строки письма
  excel/                  разбор книги, сопоставление колонок, хроника, выгрузка
  db.ts                   Prisma-клиент и адаптер
prisma/                   schema.prisma и миграции
docs/                     этот документ, модель данных, разбор файла, план
```

Правило, которое держит проект в порядке: доменные правила живут в `src/lib`
и не знают ни про HTTP, ни про React. Серверное действие валидирует вход,
вызывает домен и пишет в БД.

## 5. Права доступа

Ролей нет. Когда они появятся, роль назначается на уровне проекта, а проверка
живёт одной функцией в домене, а не россыпью проверок в действиях:

- `ADMIN` — управление участниками и настройками проектов.
- `MEMBER` — создаёт и редактирует записи в доступных проектах.
- `VIEWER` — только чтение, нужен для заказчиков и руководства.

## 6. Производительность

Ориентир скромный: три пользователя, один проект, десятки строк в каждом
реестре. Что из этого следует:

- Статус документа пересчитывается при изменении стороны и хранится в
  `Document.status`, чтобы реестр читался без агрегата по сторонам.
- Поисковая строка письма готовится при записи, а не при каждом запросе.
- Реестры читаются одним запросом со связями, без N+1.
- Пагинация появится вместе с ростом переписки; сейчас она была бы ответом на
  несуществующую проблему.

## 7. Чувствительные данные

В системе окажется служебная переписка, персональные данные сотрудников
организаций и юридически значимые документы. Два следствия для разработки:

- Рабочие файлы заказчика не попадают в репозиторий: `*.xlsx` закрыт в
  `.gitignore`. Разбор в [docs/excel-analysis.md](excel-analysis.md) описывает
  только структуру — ни фамилий, ни ссылок на ЭДО, ни содержания переписки.
- Сиды для разработки наполняются синтетическими данными, а не срезом
  рабочего файла.
