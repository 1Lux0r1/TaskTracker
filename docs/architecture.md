# Архитектура TaskTracker

Документ фиксирует стек, границы системы и принятые по умолчанию решения.
Репозиторий на момент написания был пустым, поэтому стек выбран с нуля —
если требования аналитика изменят вводные, правки вносим сюда же.

## 1. Что мы строим

Система ведения проекта, которая заменяет набор рабочих таблиц Excel, живущих
рядом с Jira: реестр переписки ЭДО, реестры задач по трекам, матрицы
подписания юридически значимых документов, график интеграций с контрагентами и
отчёт руководству.

Разбор рабочего файла заказчика — в [docs/excel-analysis.md](excel-analysis.md);
он и задаёт требования ниже.

Следствия для архитектуры:

- Система ведёт **три разных вида записей**: работу (задачи), переписку
  (письма) и документы со сторонами подписания. Это не одна сущность с разными
  метками, у каждой свой жизненный цикл и свои реквизиты.
- Реестровое представление с инлайн-редактированием — представление первого
  класса. Люди пришли из таблиц и будут работать так же.
- Импорт существующего файла и выгрузка любого реестра в Excel — часть MVP.
  Выгрузка остаётся навсегда: отчётность наружу идёт в Excel.
- Хроника важнее статуса. В исходных таблицах колонка «Статус» содержит ленту
  событий с датами, и эту ленту надо сохранить как ленту.
- Отчёт руководству — замораживаемый снимок, а не живая выборка.
- Производственный трек остаётся в Jira. Система хранит ключ задачи и
  подтягивает статус, а своими задачами ведёт официальный и юридический треки,
  которых в Jira нет.

## 2. Стек (решения по умолчанию)

| Слой | Выбор | Почему именно так |
| --- | --- | --- |
| Язык | TypeScript (strict) | Один язык на фронте и бэке, общие типы модели данных |
| Фреймворк | Next.js 15, App Router, React 19 | Фулстек в одном деплое, серверные компоненты для тяжёлых таблиц |
| API | tRPC | Типы моделей приезжают на клиент без кодогенерации и без ручной синхронизации схем |
| БД | PostgreSQL 16 | Рекурсивные CTE для дерева задач и графа зависимостей, JSONB для пользовательских полей |
| ORM | Prisma | Версионированные миграции, схема как единый источник правды по модели |
| Аутентификация | Auth.js (NextAuth v5) | Email-ссылка на старте, OAuth-провайдер добавляется конфигом |
| UI | Tailwind CSS + shadcn/ui | Ненавязчивая база, компоненты правим у себя, а не боремся с темой библиотеки |
| Таблица | TanStack Table v8 | Виртуализация, группировка, инлайн-редактирование на больших списках |
| Гант | своя SVG-реализация поверх модели дат | Готовые библиотеки Ганта плохо дружат с нашей моделью зависимостей |
| Фоновые задачи | pg-boss (очередь в самом Postgres) | Импорт, пересчёт расписания, уведомления без отдельного брокера |
| Excel | ExcelJS | Чтение исходного файла и выгрузка реестров в привычном виде |
| Тесты | Vitest + Playwright | Юнит на домен, e2e на критичные сценарии |
| Запуск | Docker Compose | Одинаково на машине разработчика и на сервере |

### Что сознательно НЕ берём в MVP

- Отдельный бэкенд-сервис (Nest/Go) — при одной команде это лишняя граница.
- Микросервисы, Kafka, Redis — нет нагрузки, которая их оправдывает.
- Realtime через WebSocket — начинаем с оптимистичных обновлений и
  инвалидации кэша; realtime добавляем, когда появятся жалобы на конфликты.
- Kubernetes — один контейнер и Postgres закрывают первые месяцы.

## 3. Масштаб

Старт: один проект, три человека. Отсюда два решения.

Пространство (`Workspace`) в модели остаётся, но в интерфейсе MVP не
показывается: одна строка ничего не стоит, а при масштабировании изоляция
данных уже будет на месте.

Требования к производительности снимаются почти полностью — кроме реестра
переписки. В исходном файле он уже больше тысячи строк и растёт быстрее всего,
поэтому пагинация по курсору и индексы по дате и сроку нужны сразу, а не
«когда упрёмся».

## 4. Границы и структура кода

```
apps/web/                 Next.js: страницы, серверные компоненты, tRPC-роутеры
  src/app/                маршруты
  src/server/api/         tRPC-роутеры (тонкие, только валидация + вызов домена)
  src/server/domain/      бизнес-логика: подписание, сроки, отчёты, права
    signing/              вывод статуса документа из статусов сторон
    letters/              расчёт просрочки, связь письмо ↔ задача ↔ документ
    reports/              сборка и заморозка отчёта за период
    import/               разбор файла, сопоставление колонок и контрагентов
  src/server/db/          Prisma-клиент, репозитории
packages/shared/          zod-схемы и типы, общие для клиента и сервера
prisma/                   schema.prisma и миграции
docs/                     этот документ, модель данных, план MVP
```

Правило, которое держит проект в порядке: бизнес-логика живёт в
`server/domain` и не знает ни про HTTP, ни про React. tRPC-роутер только
валидирует вход и вызывает домен. Это даёт возможность позже вынести домен в
отдельный сервис, если он всё-таки понадобится.

## 5. Права доступа

Роль назначается на уровне рабочего пространства и может быть переопределена
на уровне проекта:

- `OWNER` — всё, включая удаление пространства и управление биллингом.
- `ADMIN` — управление участниками и настройками проектов.
- `MEMBER` — создаёт и редактирует задачи в доступных проектах.
- `VIEWER` — только чтение, нужен для заказчиков и руководства.

Проверка прав — единая функция в домене, которая принимает
`(userId, resource, action)`. Ни один tRPC-роутер не проверяет права сам.

## 6. Производительность

Ориентир для MVP скромный: три пользователя, один проект. Реальные объёмы
берём из исходного файла — около 1100 строк переписки и по паре десятков строк
в остальных реестрах. Что из этого всё же следует:

- Реестры всегда работают с пагинацией по курсору. Переписка растёт быстрее
  всех, и единственный реестр, который упрётся в объём, — именно она.
- Дерево задач читается одним рекурсивным CTE, а не N+1 запросами.
- Статус документа пересчитывается при изменении стороны и хранится в
  `Document.state`, чтобы реестр документов читался без агрегата по сторонам.
- Пересчёт дат по зависимостям — фоновая задача на уровне проекта, а не
  синхронно в запросе сохранения задачи.
- Индексы описаны рядом с моделью в `docs/data-model.md`.

## 7. Чувствительные данные

В системе окажется служебная переписка, персональные данные сотрудников
контрагентов и юридически значимые документы. Два следствия для разработки:

- Рабочие файлы заказчика не попадают в репозиторий. Разбор в
  `docs/excel-analysis.md` описывает только структуру: ни фамилий, ни ссылок
  на ЭДО, ни содержания переписки.
- Сиды для разработки наполняются синтетическими данными, а не срезом
  рабочего файла.
