# Переезд с Excel: импорт существующих таблиц

Документ отвечает на два вопроса: какие колонки куда ложатся и что делать с тем,
что не ложится. Построен на реальном файле пользователя — его разбор отдельно:
[source-files.md](source-files.md).

Файл содержит пять разных реестров на восьми листах, поэтому импорт не один, а три:
задачи, письма ЭДО и документы на подписании. Ниже — карта по каждому.

---

## 1. Задачи

Источник: листы «Внутренние задачи», «Внешние задачи», «Задачи Производственные».
Структура у них одинаковая, отличается только колонкой внешнего ответственного.

| Колонка в файле | Поле в приложении | Как разбирается |
|---|---|---|
| Дата создания | `task.created_at` | Настоящая дата, разбирается как есть |
| Письмо, задача, поручение | `task.title` + `task.description` | Первая строка — название, остальное — описание. Значения длинные, часто в несколько предложений |
| Ответственный | `task.assignee` + `task.watchers` + примечание | Фамилия без имени. «Фамилия, Фамилия» → первый основной, остальные соисполнители. «Фамилия — техническая часть / Фамилия — письмо» → оба в соисполнители, исходный текст в примечание |
| Ответственный от ДИТ | `task.assignee` | Только на листе внешних задач |
| Внешний ответственный | `task.external_contact` | Организация и ФИО одной строкой, отдельное поле |
| Плановый срок | `task.due_date` | Заполнен у 7 задач из 20. Остальные импортируются без срока и попадают в отдельный список «без срока» после импорта |
| Статус | **разбирается на две части** | Смотри ниже |
| Результат (ссылки на ЭДО, комментарии) | `task.links` + комментарий | Ссылка вытаскивается отдельно, остальной текст — в комментарий |
| — | `task.track` | Проставляется по листу-источнику: внутренний / внешний / производственный |

**Про колонку «Статус».** В файле это не справочник, а журнал: «05.05.2026 драфт письма
загружен в ЭДО / 06.05.2026 на согласовании». Разбирается так: из текста вытаскиваются
пары «дата + событие», каждая становится записью в истории задачи, а текущий статус
определяется по последнему событию и словарю:

- **Готово** ← «Выполнено», «Выполнено <дата>», «Ответ ушёл», «Данные направили»
- **На согласовании** ← «На согласовании у <кого>», «на согласовании»
- **В работе** ← «драфт загружен», «прислала драфт, надо проверить», любой текст с датой
- **Не начата** ← пусто

Свести всю эту колонку в одно поле нельзя — потеряется половина фактуры, ради которой
её и вели.

## 2. Письма ЭДО

Источник: лист «Письма ЭДО». 1006 строк, из них с данными — 50.

| Колонка в файле | Поле в приложении | Как разбирается |
|---|---|---|
| № | — | Не импортируется, номер выдаёт приложение. Хранится как 1.0, 2.0 — дробные |
| Номер письма | `letter.number` | Служебный номер, остаётся как есть |
| Дата письма | `letter.date` | Настоящая дата |
| Тема | `letter.subject` | |
| Ссылка на письмо | `letter.edo_url` | Берётся гиперссылка ячейки, если её нет — текст |
| Тип | `letter.direction` | Входящее / Исходящее, ровно два значения |
| Контрагент | `letter.counterparty` | 14 различных организаций — становятся справочником |
| Срок исполнения | `letter.due_date` | Заполнен у 17 писем из 50 |
| Просроченные | **не импортируется** | Это формула. Логика повторяется в приложении: если статус «Подписано» или «Дан ответ» — исполнено, иначе сравнение срока с сегодняшним днём |
| Ответ реквизиты | `letter.reply_ref` | Номер и дата ответного письма |
| Статус | `letter.status` | Подписано · Принято к сведению · Дан ответ · В работе · Ответ на согласовании · На согласовании у <кого> |
| Задача в Jira | `letter.jira_key` | Ссылка на внутренний трекер, ключ вытаскивается из URL |
| Комментарий | `letter.note` | |

**Обязательное правило:** строка, в которой заполнен только «№», пропускается.
Иначе из этого листа приедет тысяча пустых писем.

## 3. Документы на подписании

Источник: листы «Регламенты инф. взаимодействия», «ДС к NDA», «График интеграций с РСО».
Это самая нестандартная часть: строка здесь — не задача, а **документ с несколькими
подписывающими сторонами**, а колонки — стадии.

Модель, в которую это ложится:

```
Документ (регламент / допсоглашение / …)
  ├── контрагент
  ├── ответственный
  ├── срок
  ├── Подписи: сторона → статус → дата → письмо-основание → ссылка на ЭДО
  │     ДИТ        Подписан
  │     Контрагент Подписан
  │     ДЖКХ       Нет
  └── Актуальная задача (что сделать, чтобы двинуть документ дальше)
```

| Колонка в файле | Поле в приложении |
|---|---|
| РСО | `document.counterparty` |
| Статус ДИТ / Статус подписания ДИТ | `signature[ДИТ].status` |
| Статус подписания РСО | `signature[контрагент].status` |
| Статус подписания ДЖКХ | `signature[ДЖКХ].status` |
| Актуальный статус | `document.summary` — свободный текст про экземпляры |
| Актуальные задачи | превращается в **задачу** со ссылкой на документ |
| Ответственный | `document.owner` |
| Письмо из ДИТ (дата и №) | `document.outgoing_letter` → связь с письмом ЭДО |
| Ссылка на ЭДО | `document.edo_url` |
| Письмо с ответом | `document.incoming_letter` → связь с письмом ЭДО |
| Срок интеграции, факт | `document.deadline` |
| Статус согласования | журнал документа, свободный текст |
| Итоговый статус подписания | `document.final_status` |

Значения статусов подписания: Заслан · Подписан · Нет · Согласован · Не согласован ·
Отправлен. Шесть значений, справочник фиксированный.

Лист «График интеграций» ложится сюда же, но колонки там — не стороны, а **вехи**:
дата отправки регламента, дата подписания, готовность системы контрагента, интеграция
в dev, открытие в тестовой среде. Это пять контрольных точек на контрагента, и они
становятся вехами документа, а не отдельными задачами.

## 4. Отчёт руководству

Лист «Отчет АЮ» не импортируется как данные — это **шаблон отчёта**, и он разбирается
для того, чтобы приложение умело такой отчёт собирать. Его структура описана в
[экранах MVP](../ui/mvp-screens.md).

Разбор осложняет то, что одна логическая запись занимает 13 строк: первая строка —
проект, следующие — продолжения с пустыми первыми колонками. Правило: строка с пустыми
первыми колонками принадлежит предыдущей записи.

---

## Общие правила разбора

**Даты.** В файле лежат настоящие даты, не текст — это упрощает дело. Но в колонках
дат встречается текст: «Не подписан», «Финальный проект в разработке». Такое значение
уходит в статус или примечание, поле даты остаётся пустым, строка помечается.

**Ссылки.** Берётся гиперссылка ячейки, если её нет — текст. В одной ячейке часто
и текст, и ссылка: «Ответ ушёл <адрес>» — разбирается на комментарий и ссылку.

**Цвет.** В этих файлах заливка дублирует текст: зелёная там, где «Подписан», красная
там, где «Нет». Поэтому цвет игнорируется. Спросить про него нужно только там, где
ячейка закрашена, а текста нет.

**Формулы.** Берётся вычисленное значение, а колонки-формулы перечисляются в отчёте
об импорте: в приложении они перестанут пересчитываться, и человек должен об этом знать.
В этом файле такая колонка одна — «Просроченные», и её вообще не надо импортировать.

**Неопознанные колонки** не выбрасываются: сохраняются под исходным заголовком и видны
в карточке в блоке «Из исходной таблицы».

**Люди.** В файле только фамилии. Сопоставление по фамилии, при совпадении — вопрос на
шаге проверки. Ненайденный человек создаётся как внешний участник, чтобы задача не
осталась без ответственного.

---

## Мастер импорта

**Шаг 1. Файл и листы.** Показываем найденные листы с числом заполненных строк и
предлагаем тип для каждого: задачи / письма / документы на подписании / пропустить.
Строки, где заполнен только номер, в счёт не идут — показываем честное число.

**Шаг 2. Сопоставление колонок.** Отдельно для каждого типа. Автоподстановка по
словарю заголовков; неопознанное по умолчанию уходит в дополнительное поле.
Здесь же показываем найденные значения статусов и просим подтвердить сопоставление.

**Шаг 3. Проверка.** Первые 50 строк ровно в том виде, в каком лягут. Счётчики:
создаётся, с предупреждением, пропущено. Отдельно — список задач без срока, потому что
их будет много и это важно увидеть до импорта, а не после.

**Шаг 4. Импорт и отчёт.** Что создано, что пропущено и почему, какие колонки ушли в
дополнительные поля, какие были формулами. Откат импорта целиком, пока в проекте нет
ручных правок.

## Повторный импорт

В первой версии повторная загрузка создаёт новые записи, а не обновляет старые. Для
писем ЭДО это особенно важно: реестр пополняется постоянно, и дозаливка будет частой
операцией. Поэтому для писем ключ есть сразу — номер письма плюс дата: при совпадении
запись обновляется, а не дублируется. Для задач ключа нет, там честно предупреждаем.

## Возможен другой путь

Внутри файла встречаются ссылки вида `#gid=`, а это формат Google Таблиц. Если
оригинал ведётся там, а Excel — только формат обмена, то вместо загрузки файла
правильнее подключиться к Таблицам напрямую: тогда переезд можно сделать постепенным,
с синхронизацией, а не одним разовым импортом. Это нужно уточнить до начала разработки
импорта, потому что решение меняет объём работ.
