# Модель данных

Описывает схему, которая реально лежит в `prisma/schema.prisma`: двенадцать
таблиц. Почему модель именно такая — в [docs/excel-analysis.md](excel-analysis.md);
здесь только состав и правила.

## 1. Общие решения

**Статусы хранятся строками, а не перечислениями.** SQLite перечислений не
знает, поэтому словари статусов собраны в `src/lib/domain.ts` и оттуда же
берутся подписи для интерфейса и разбор значений из Excel. При переезде на
PostgreSQL строки можно превратить в enum, но выигрыш невелик, а жёсткость
мешает: словарь статусов заказчика ещё будет меняться.

**Даты события и даты записи разделены.** Событие произошло пятого, а записали
седьмого — в реестрах это обычное дело, поэтому у записи хроники есть
`occurredOn` (когда произошло) отдельно от `createdAt` (когда внесли).

**Мягкие связи.** Ответственный, контрагент, владелец — всё `SetNull` при
удалении: запись реестра не должна исчезать вместе со справочником.

## 2. Справочники

| Модель | Что это |
| --- | --- |
| `Member` | Сотрудник: исполнитель задач, владелец писем и документов, автор отчёта |
| `Counterparty` | Организация: адресат писем и сторона документов. Флаг `isInternal` отмечает нашу организацию — ту, что ведёт реестр |
| `CounterpartyAlias` | Вариант написания организации. «ПАО "Россети Московский Регион"» и «ПАО Россети МР» — одна запись, иначе отчёт по контрагенту не собрать |

## 3. Проект и работа

`Project` — верхний уровень, аналог отдельной книги Excel: код, название,
статус, сроки, владелец.

`Task` — строка реестра задач. Кроме обычного набора (статус, приоритет,
ответственный, сроки, готовность, подзадачи) у неё есть то, чего в обычном
трекере нет:

| Поле | Зачем |
| --- | --- |
| `track` | Производственный, внутренний, внешний или юридический трек. По нему собирается отчёт и делится ответственность |
| `externalAssignee` | Ответственный на стороне контрагента: заводить его сотрудников пользователями никто не будет |
| `progressNote` | Исходный текст колонки «Статус» из файла целиком — на случай, если разбор хроники ошибся |
| `resultLink` | Ссылка на результат: карточка ЭДО, документ, дашборд |
| `letterId` | Задача, выросшая из письма |
| `externalKey` | Ключ задачи в Jira или другом внешнем трекере |

`Note` — датированная запись хроники, привязанная к задаче, письму или
документу. Это ответ на главную находку разбора: колонка «Статус» в реестрах
содержит не состояние, а ленту событий с датами, и её нельзя складывать в одно
текстовое поле.

## 4. Переписка

`Letter` — письмо ЭДО, входящее или исходящее. Ключевые поля помимо очевидных:

| Поле | Зачем |
| --- | --- |
| `statusNote` | Исходный текст статуса: «На согласовании у <фамилия>» несёт больше, чем справочное значение |
| `responseRef` | Реквизиты ответа: чем письмо закрыли |
| `responseToId` | Письмо, ответом на которое является это: реестр ведёт переписку цепочками |
| `externalTaskKey` | Связанная задача во внешнем трекере |
| `searchIndex` | Номер, тема, контрагент и комментарии строчными буквами одной строкой, см. [docs/search-and-analytics.md](search-and-analytics.md) |

Уникальность — `(projectId, number, direction)`: один и тот же номер
встречается и во входящем, и в исходящем.

Просрочка полем не хранится: она считается от `dueDate` и текущей даты. В
исходном файле признак просрочки записан текстом и устаревает в тот же день.

## 5. Подписание

`Document` — юридически значимый документ: регламент, допсоглашение, контракт.
`DocumentSignature` — подпись одной стороны, по записи на сторону,
уникальность `(documentId, party)`.

Итоговый статус документа **выводится** из статусов сторон функцией
`deriveDocumentStatus` в `src/lib/domain.ts`:

- отказ хотя бы одной стороны → отказ;
- подписали все обязательные → подписано;
- подписал кто-то один → в процессе подписания;
- стороны не заданы → статус документа как есть.

Вывод перебивается явно: если в итоговой колонке реестра записан отказ, статус
документа — отказ, чем бы ни закончились отдельные стороны. Без этого отказ
теряется: в реестре допсоглашений он записан только в итоговой колонке.

Сторона связывается с организацией из справочника: колонка «Статус подписания
РСО» подставляет контрагента строки, остальные стороны ищутся по названию. Без
этой связи нельзя ответить на главный вопрос по документу — ждёт он нашей
подписи или чужой. Причём «чужая» не равно «контрагент»: соседний департамент
подписывает вместе с нами, но нашей стороной не является, поэтому свою
организацию отмечают флагом, а не выводят из отсутствия связи.

У подписи есть `refusalReason` (отказ без причины нечем отрабатывать),
`basisLetterId` (письмо, которым документ ушёл стороне или которым она
ответила), `sentAt` / `respondedAt` / `signedAt`.

## 6. График интеграций и отчёт

`CounterpartyMilestone` — матрица «контрагент × этап» с плановой и фактической
датой. Это не вехи проекта: строка исходного реестра — организация, колонка —
этап.

`WeeklyReport` — отчёт руководству за период. Собирается системой из закрытых
задач и подписанных документов, правится руками и **замораживается** при
отправке: `state = SUBMITTED` запрещает правку на сервере. Живая выборка через
неделю покажет не то, что ушло руководству, и сверить её будет нельзя.

`ImportBatch` — журнал загрузок: файл, лист, сколько строк принято, отклонено
и с какими ошибками.

## 7. Чего в модели нет

Перечислено не как недоработка, а как осознанно отложенное. Почти всё это было
в расширенной схеме из PR #1; в базу взято не было, потому что на одном
проекте и трёх людях не окупается.

| Чего нет | Когда понадобится |
| --- | --- |
| Пользователи, роли, пространства | До реальной эксплуатации: в системе служебная переписка |
| Несколько ответственных у задачи | Когда перестанет хватать пары «ответственный + внешний ответственный». В исходном файле пара фамилий в ячейке встречается, полный текст сохраняется в хронике |
| Зависимости задач и пересчёт сроков | Когда появится планирование, а не ведение реестров. В исходном файле зависимостей нет вообще |
| Метки, вложения, учёт времени | По запросу: в исходных таблицах их нет |
| Журнал изменений (кто и что поправил) | Вместе с ролями — до этого некого записывать |
| Сохранённые фильтры | Когда наборы фильтров устоятся; сейчас фильтр живёт в адресе страницы и ссылку можно сохранить в браузере |
| Производственный календарь (нерабочие дни) | Когда просрочку начнут считать в рабочих днях |
| Снимки метрик по дням | Когда понадобится динамика, а не срез на сегодня |
| Разбивка отчёта по трекам отдельными блоками | Сейчас текст отчёта — четыре поля целиком; разбивка по трекам появится, когда отчёт начнут собирать несколько человек |
