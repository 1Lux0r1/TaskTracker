# Модель данных TaskTracker

Единый источник правды — `prisma/schema.prisma`. Этот документ объясняет
смысл сущностей и решения, которые из схемы не видны.

Модель построена на разборе рабочего файла заказчика — см.
[docs/excel-analysis.md](excel-analysis.md). Там же обоснование сущностей,
которых в обычном трекере задач нет: писем, документов со сторонами
подписания и замораживаемых отчётов.

## 1. Карта сущностей

```
Workspace ──┬── Membership ──── User
            │
            ├── Counterparty ──── CounterpartyAlias
            │
            ├── Project ──┬── Task ──┬── TaskAssignee ──── User
            │             │          ├── TaskDependency (task ↔ task)
            │             │          ├── Note          (лента с датами событий)
            │             │          ├── Comment / Attachment / TimeEntry
            │             │          ├── LetterTask ──── Letter
            │             │          ├── DocumentTask ── Document
            │             │          └── TaskLabel ──── Label
            │             │
            │             ├── Letter ──┬── Note
            │             │            └── Letter (ответ на письмо)
            │             │
            │             ├── Document ┬── DocumentParty ── Counterparty
            │             │            │      └── Letter (письмо-основание)
            │             │            └── Note
            │             │
            │             ├── CounterpartyMilestone (график интеграций)
            │             ├── StatusReport ── ReportSection ── Track
            │             ├── Track
            │             ├── ProjectStatus  (статусы задач проекта)
            │             ├── Milestone
            │             └── ProjectMember  (переопределение роли)
            ├── CustomFieldDef
            └── ActivityLog
```

Три группы сущностей: **работа** (задачи, треки, вехи), **переписка и
документы** (письма, документы, стороны подписания) и **отчётность**
(замораживаемые снимки за период). Связывает их проект и справочник
контрагентов.

## 2. Сущности и назначение

### Workspace
Верхняя граница изоляции данных. Все запросы фильтруются по `workspaceId` —
это же и защита от утечки данных между организациями, если позже появится
мультиарендность.

### User и Membership
`User` — учётная запись. `Membership` связывает пользователя с пространством и
несёт роль. Пользователь может быть в нескольких пространствах.

### Project
Проект — контейнер задач со своим набором статусов, своими вехами и своей
датой начала/окончания. Плановые даты проекта (`plannedStart`, `plannedEnd`)
хранятся отдельно от фактических (`actualStart`, `actualEnd`) — сравнение этих
двух пар и есть базовый отчёт об отклонениях, который в Excel считали руками.

### ProjectStatus
Статусы задач настраиваются на уровне проекта, а не зашиты в enum. Причина
простая: в Excel у каждой команды свой набор колонок-состояний, и жёсткий
список статусов сразу ломает миграцию. Поле `category` (`TODO` / `IN_PROGRESS`
/ `DONE` / `CANCELLED`) даёт системе понимание, что считать выполненным, при
любых пользовательских названиях.

### Task
Центральная сущность. Ключевые решения:

- **Иерархия** через `parentId` — подзадачи любой глубины. Читается рекурсивным
  CTE; в приложении ограничиваем вложенность пятью уровнями, чтобы UI не
  разъезжался.
- **Даты**: плановые (`plannedStart`, `plannedEnd`), фактические
  (`actualStart`, `actualEnd`) и отдельный `dueDate` — срок, обещанный
  заказчику. Это три разные вещи, и в Excel их постоянно путали.
- **Оценка и факт**: `estimateHours` и агрегированный `loggedHours`
  (пересчитывается из `TimeEntry`).
- **Исполнители**: связь многие-ко-многим через `TaskAssignee`, потому что
  реальные задачи часто делают вдвоём. Один из исполнителей помечен
  `isPrimary` — он и попадает в колонку «Ответственный».
- **Порядок**: `sortOrder` типа `Decimal` — вставка между двумя задачами не
  требует перенумерации всего списка.
- **Пользовательские поля**: `customFields` типа `JSONB`. Определения полей
  живут в `CustomFieldDef`, значения — в этом JSONB. Причина выбора: колонки
  в Excel у всех разные, а отдельная таблица «значение поля» превращает любую
  выборку таблицы в тяжёлый join.

### TaskDependency
Граф зависимостей между задачами. Тип связи — `FINISH_TO_START` (по умолчанию),
`START_TO_START`, `FINISH_TO_FINISH`, `START_TO_FINISH`, плюс `lagDays` для
задержки. Циклы запрещены: перед вставкой домен проверяет достижимость
рекурсивным CTE и отклоняет связь, замыкающую цикл.

Пересчёт дат при сдвиге задачи-предшественника — фоновая задача. В MVP
поведение по умолчанию: **предлагать** сдвиг зависимых задач, а не применять
автоматически. Автоматический сдвиг календаря без подтверждения — самый
быстрый способ потерять доверие к системе на переезде из Excel.

### Milestone
Веха проекта: дата и признак достижения. Задачи ссылаются на веху
необязательным `milestoneId`.

### TimeEntry
Списание времени: задача, пользователь, дата, часы, комментарий. Отдельная
таблица, а не поле в задаче, потому что нужны отчёты по человеку и по периоду.

### Comment и Attachment
Обсуждение и файлы на задаче. Вложения в MVP — метаданные в БД плюс файл в
S3-совместимом хранилище; в БД лежит только ключ объекта.

### ActivityLog
Журнал изменений: кто, когда, какое поле какой сущности изменил, старое и
новое значение. Пишется в домене одним хелпером на каждое изменение, а не
триггерами БД — чтобы в записи был контекст действия пользователя, а не только
дифф строки.

### CustomFieldDef
Определение пользовательского поля: имя, ключ в JSONB, тип
(`TEXT` / `NUMBER` / `DATE` / `SELECT` / `MULTI_SELECT` / `CHECKBOX` / `USER`),
варианты для select, обязательность, область (пространство или проект).

### Track
Трек работ внутри проекта: официальный, юридический, производственный,
аналитический. По трекам разделяется ответственность и собирается отчёт
руководству — в исходном файле отчёт прямо структурирован по ним.

### Counterparty и CounterpartyAlias
Справочник организаций: контрагенты и собственные подразделения
(`isInternal`). На них ссылаются задачи, письма, документы, стороны подписания
и вехи интеграции.

`CounterpartyAlias` хранит варианты написания. В исходном реестре одна
организация встречается минимум в четырёх написаниях, и без схлопывания отчёт
по контрагенту не собирается. При импорте строка ищется по каноничному имени и
по алиасам; новое написание человек либо привязывает к существующей
организации, либо заводит как новую.

### Letter
Письмо ЭДО: номер, дата, тема, направление (входящее или исходящее),
контрагент, срок исполнения, статус, ссылка на карточку в ЭДО, реквизиты
ответа, ключ задачи в Jira, ответственный.

Три решения, которые стоит объяснить:

- **Письмо — не задача.** У него свой жизненный цикл и свои реквизиты
  (номер, реквизиты ответа, карточка в ЭДО), которых у задачи нет. Связь с
  задачами — многие-ко-многим через `LetterTask`.
- **Просрочка не хранится.** Считается как `dueDate < сегодня` при незакрытом
  статусе. В исходной таблице она записана текстом («просрочка 49 дн.») и
  устаревает в тот же день.
- **Реквизиты ответа хранятся и текстом, и ссылкой.** `responseRequisites` —
  как их пишут в реестре, `responseToId` — ссылка на ответное письмо, когда
  оно заведено в системе. Требовать заведения обоих писем нельзя: часть
  переписки в систему не попадёт.

### Document и DocumentParty
Юридически значимый документ: регламент, NDA, дополнительное соглашение,
контракт, акт.

`DocumentParty` — ключевое решение всего юридического трека. В исходном
реестре у документа три независимые колонки статуса подписания, по одной на
сторону. Линейный статус такое не выражает, поэтому стороны вынесены в
отдельную таблицу: у каждой свой статус, свои даты отправки, ответа и
подписания, своё письмо-основание и свой ответственный.

Статусы стороны взяты из реальных значений в файле: `NOT_SENT`, `SENT`,
`UNDER_REVIEW`, `AGREED`, `SIGNED`, `REFUSED`. Отказ — отдельное состояние, и
причина при нём обязательна: в файле встречается отказ со ссылкой на
секретность, и без причины такая строка бесполезна.

Поле `Document.state` выводится из статусов сторон и пересчитывается при
каждом их изменении. Хранится денормализованно, чтобы реестр документов
читался одним запросом без агрегата по сторонам. Правило вывода: есть отказ —
`REJECTED`; подписали все — `SIGNED`; подписал кто-то — `PARTIALLY_SIGNED`.

Поле `stateNote` — свободная пометка вроде «в наличии в 3 экз.»: она не
выводится из статусов, но в реестре нужна.

### CounterpartyMilestone
График интеграций: строка — контрагент, колонка — этап (регламент отправлен,
регламент подписан, готовность системы контрагента, интеграция в dev, открытие
в тестовой среде). Плановая и фактическая дата по каждому этапу.

Это матрица «контрагент × этап», и вехами проекта она не выражается: веха
проекта одна на проект, а здесь свой набор дат у каждой из организаций.

### Note
Датированная запись в ленте задачи, письма или документа.

Сущность появилась из разбора файла: колонка «Статус» в реестрах задач
содержит не статус, а хронику с датами. Поэтому у задачи есть и статус из
списка, и лента записей.

`occurredOn` — дата события, отдельная от `createdAt`: событие было пятого
числа, а записали седьмого. При импорте в неё попадает дата, распарсенная из
текста ячейки.

### SavedFilter
Сохранённый набор условий для реестра писем, задач или документов: личный или
общий на пространство, с закреплением в боковой панели. Дерево условий в
JSONB.

Поля и операторы валидируются схемой на сервере: сохранённый фильтр — это
структура данных, а не кусок запроса. Подробности в
[docs/search-and-analytics.md](search-and-analytics.md).

### NonWorkingDay
Производственный календарь: нерабочие дни и переносы (`isWorkingDay = true`
для рабочей субботы). Нужен потому, что сроки официальной переписки
исчисляются в рабочих днях.

### MetricSnapshot
Суточный срез значения метрики с разрезом по контрагенту, треку или
исполнителю. Текущие значения считаются запросом по живым данным, а снимки
нужны только для графиков динамики: восстановить «сколько было просрочено
месяц назад» по журналу изменений дороже и менее надёжно, чем записать
значение в тот день.

### StatusReport и ReportSection
Отчёт руководству за период. Шапка — руководитель проекта, наличие контракта,
ближайший релиз, план развития. Разделы — по трекам, в каждом: выполнено за
период, блокеры, предлагаемые решения, план на следующий период, ответственные
за заполнение.

Два решения:

- **Отчёт собирается системой, но правится руками.** «Блокеры» и
  «предлагаемые решения» — аналитика, а не выборка из задач. Система
  заполняет то, что может, остальное дописывает человек.
- **После отправки отчёт замораживается** (`state = SUBMITTED`). Если он
  остаётся живой выборкой, то через неделю покажет не то, что ушло
  руководству, и сверить его будет нельзя.

Период задаётся датами, а не зашит: в файле он двухнедельный, заказчик
говорит о еженедельном.

## 3. Что живёт в SQL, а не в Prisma

Часть модели описана отдельной миграцией, потому что Prisma этого не выражает:

- **Генерируемые колонки поиска**: `tsvector` для полнотекстового поиска и
  приведённые к нижнему регистру копии текста для поиска по фрагменту, плюс
  `Letter.numberDigits` — номер без разделителей.
- **Индексы** `pg_trgm` и GIN по этим колонкам, а также GIN по
  `Task.customFields`.
- **Представление `calendar_event`** — все даты проекта из разных сущностей в
  одной выборке. Отдельной таблицы событий нет сознательно: дублировать дату
  значит держать две правды.
- **Представление `document_signing_state`** — состояние подписания по
  сторонам, опора для воронки и для ответа «на какой стороне документ стоит».

Источник правды для базы — папка миграций, для клиента Prisma —
`schema.prisma`. Расхождения нет: миграции создают всё, включая то, чего в
схеме Prisma не описано.

## 4. Связь с Jira

Производственный трек команда ведёт в Jira, и требование заказчика —
наглядность и отчётность, а не замена трекера разработки. Поэтому решение по
умолчанию: производственные задачи остаются в Jira, а система хранит ключ
задачи (`Task.jiraKey`, `Letter.jiraKey`) и подтягивает её статус. Собственные
задачи заводятся для официального и юридического треков, которых в Jira нет.

Это снимает перенос истории разработки и убирает двойной ввод. Связь
необязательная: если заказчик захочет уйти из Jira полностью, модель это
выдержит.

## 5. Индексы, которые нужны сразу

| Таблица | Индекс | Зачем |
| --- | --- | --- |
| `Task` | `(projectId, statusId, sortOrder)` | основное табличное представление и доска |
| `Task` | `(workspaceId, dueDate)` | «что горит» по всем проектам |
| `Task` | `(parentId)` | обход дерева подзадач |
| `Task` | GIN по `customFields` | фильтры по пользовательским полям |
| `TaskAssignee` | `(userId, taskId)` | «мои задачи» |
| `TaskDependency` | `(fromTaskId)` и `(toTaskId)` | обход графа в обе стороны |
| `TimeEntry` | `(userId, date)` | отчёты по списанию времени |
| `ActivityLog` | `(entityType, entityId, createdAt)` | история конкретной сущности |
| `Letter` | `(projectId, dueDate)` | реестр переписки и расчёт просрочки |
| `Letter` | `(projectId, letterDate)` | реестр по датам, основное представление |
| `CounterpartyAlias` | `(alias)` | сопоставление написаний при импорте |
| `DocumentParty` | `(documentId, position)` | матрица подписания в реестре документов |
| `Note` | `(taskId, occurredOn)` и аналоги | лента событий в хронологии |
| `Task` | `(jiraKey)` | синхронизация с Jira |
| `Letter` | GIN по `searchVector`, триграммы по номеру и теме | поиск по словам и по фрагменту |
| `Note` | GIN по `searchVector`, триграммы по тексту | поиск по хронике |
| `MetricSnapshot` | `(projectId, metric, capturedOn)` | графики динамики |
| `SavedFilter` | `(workspaceId, subject, position)` | список фильтров в панели |

## 6. Осознанно отложено

- **Версионирование задач** (полные снапшоты) — пока достаточно `ActivityLog`.
- **Связи между проектами** (зависимость проекта от проекта) — появится вместе
  с портфельным представлением.
- **Загрузка ресурсов** (capacity planning) — нужны рабочие календари и
  ставки; отдельный этап после MVP.
- **Мягкое удаление везде** — в MVP `deletedAt` есть только у `Task` и
  `Project`, остальное удаляется физически. Исключение стоит обсудить для
  документов: у юридического трека удаление строки может понадобиться
  обратимым.
- **Маршруты согласования** (кто за кем подписывает, автоматический переход к
  следующей стороне) — в MVP порядок сторон задаётся полем `position`, а
  движение по нему делает человек.
- **Электронная подпись внутри системы** — система отражает подписание,
  происходящее в ЭДО, но сама ничего не подписывает.
- **Двусторонняя синхронизация с Jira** — в MVP только чтение статуса по
  ключу задачи.
