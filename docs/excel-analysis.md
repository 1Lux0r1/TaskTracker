# Разбор рабочего файла заказчика

Разбор приложенного файла Excel (8 листов). Документ описывает только
структуру: названия колонок, словари статусов и объёмы. Персональные данные,
ссылки на ЭДО и содержание переписки сюда не переносятся — они останутся в
системе, а не в репозитории.

Этот разбор — основание для правок модели данных, а не пересказ файла.

## 1. Что оказалось в файле

| Лист | Строк с данными | Что это по сути |
| --- | --- | --- |
| Письма ЭДО | ~1006 | Реестр входящей и исходящей переписки |
| Внутренние задачи | 20 | Поручения внутри подразделения |
| Внешние задачи | 2 | Поручения с ответственным на стороне контрагента |
| Задачи производственные | 3 | Производственный трек |
| Регламенты информационного взаимодействия | 9 | Матрица подписания документа тремя сторонами |
| ДС к NDA | 9 | То же для дополнительных соглашений |
| График интеграций с РСО | 9 | Вехи интеграции по каждому контрагенту |
| Отчёт руководству | 13 | Сводка по проекту за две недели |

Главное наблюдение: это не один реестр задач, а **восемь разных реестров с
разными смыслами**, которые объединяет проект и общий справочник
контрагентов. Реестр переписки на порядок объёмнее всех остальных вместе
взятых.

## 2. Что из этого следует для модели

### 2.1. Письмо — самостоятельная сущность, а не задача

Колонки листа переписки: номер письма, дата, тема, ссылка на ЭДО, тип
(входящее или исходящее), контрагент, срок исполнения, признак просрочки,
реквизиты ответа, статус, **задача в Jira**, комментарий.

У письма свой жизненный цикл (статусы: «Дан ответ», «Подписано», «Принято к
сведению», «Ответ на согласовании», «в работе») и свои реквизиты, которых нет
у задачи. Попытка представить письмо задачей потеряет номер, реквизиты ответа
и связь с ЭДО.

Признак просрочки в файле записан текстом — «просрочка 49 дн.», «исполнено».
Это вычисляемое значение, и его надо считать, а не хранить: в таблице оно
устаревает в тот же день.

### 2.2. Подписание — матрица сторон, а не один статус

У листа регламентов четыре отдельные колонки статуса: статус отправки и три
независимых статуса подписания — по одной на каждую сторону. Плюс отдельно
«статус согласования» и «итоговый статус подписания».

Линейный статус документа такое не описывает. Нужна таблица сторон документа,
где у каждой стороны свой статус, своя дата и своё письмо-основание. Итоговый
статус выводится из статусов сторон, а не вводится руками.

Реальные значения статусов сторон: «Нет», «Отправлен», «Заслан», «Согласован»,
«Подписан», «Не согласован РСО», и отказ с причиной («Отказали в подписании,
сославшись на секретность»). Отказ — отдельное состояние с обязательной
причиной, а не разновидность «не подписано».

### 2.3. Колонка «Статус» в реестрах задач содержит не статус

Это главная находка. Примеры реальных значений из листа внутренних задач:

- «05.05.2026 драфт письма загружен в ЭДО / 06.05.2026 на согласовании»
- «На согласовании у РВ с 29.04.2026»
- «Коллега прислала драфт, надо проверить» (в файле — фамилия)
- «Выполнено 20.05.2026»

На 20 строк приходится 9 уникальных значений, и почти каждое — хроника с
датами, а не состояние. Люди ведут в этой ячейке ленту событий, потому что
больше негде.

Отсюда требование: у задачи должны быть **и** статус из списка, **и** лента
датированных записей. Причём дата записи задаётся пользователем (событие было
пятого числа, а записали седьмого), поэтому дата события хранится отдельно от
даты создания записи. Наивный импорт, который положит этот текст в поле
статуса, уничтожит самую ценную часть файла.

### 2.4. Контрагенты пишутся по-разному и нуждаются в справочнике

В реестре переписки 14 уникальных написаний контрагента, среди которых одна и
та же организация встречается минимум в четырёх вариантах написания, включая
вариант с двумя организациями в одной ячейке.

Отчёт по контрагенту на таких данных не собирается. Нужен справочник
организаций с альтернативными написаниями, а при импорте — сопоставление
строки со справочником с подтверждением человеком.

### 2.5. Треки — это измерение, которого не было в модели

Отчёт руководству прямо структурирован по трекам: официальный, юридический,
анализ территории, разработка. Листы реестров делят задачи по тому же
принципу: внутренние, внешние, производственные.

Трек — не статус и не метка, а признак, по которому собирается отчёт и
разделяется ответственность. В модели он становится отдельной сущностью
уровня проекта.

### 2.6. Ответственный — почти всегда несколько человек

Реальные значения: один человек, двое через запятую, и вариант с разделением
зон ответственности прямо в ячейке («первый — техническая фактура, вторая —
переписка»). У внешних задач ответственных двое по определению: свой и на
стороне контрагента, и внешний в системе не заведён.

Связь «многие ко многим» в модели это уже покрывает. Добавить надо внешнего
ответственного — текстом с привязкой к контрагенту, потому что заводить
сотрудников контрагента как пользователей никто не будет.

### 2.7. График интеграций — вехи на контрагента, а не на проект

Этапы: отправка регламента, подписание регламента, готовность системы
контрагента, интеграция в dev-среде, открытие в тестовой среде. Строка — один
контрагент, колонка — этап.

Это матрица «контрагент × этап», а не вехи проекта. Вехи проекта из исходной
модели её не выражают.

### 2.8. Отчёт руководству — замораживаемый снимок, а не живая выборка

Колонки: проект, руководитель, наличие контракта, релиз, план развития,
выполненные работы за период, ответственные за заполнение, текущие блокеры,
предлагаемые решения, запланированные работы на следующий период,
ответственные за заполнение.

Период в файле — две недели, хотя заказчик говорит о еженедельном отчёте.
Значит период настраивается.

Два требования, которые из этого следуют. Первое: отчёт собирается системой
из задач, но потом правится руками — половина колонок («предлагаемые решения»,
«блокеры») это аналитика, а не данные. Второе: после отправки отчёт
замораживается. Если отчёт остаётся живой выборкой, то через неделю он
покажет не то, что ушло руководству, и сверить его будет нельзя.

### 2.9. Jira остаётся

В реестре переписки есть колонка со ссылкой на задачу в Jira. Производственный
трек команда ведёт в Jira, и требование заказчика — наглядность и отчётность,
а не замена трекера разработки.

Поэтому решение по умолчанию: **производственные задачи остаются в Jira**,
система хранит ключ задачи и подтягивает её статус, а собственные задачи
заводит для официального и юридического треков, которых в Jira нет. Это
снимает необходимость переносить историю разработки и убирает двойной ввод.

Если заказчик захочет полностью уйти из Jira, модель это выдержит: связь с
Jira необязательная.

## 3. Что это меняет в исходной модели

| Было | Стало |
| --- | --- |
| Задача — единственная сущность работы | Добавлены письмо, документ и сторона подписания |
| Статус задачи — одно поле | Статус плюс лента датированных записей |
| Контрагентов нет | Справочник организаций с альтернативными написаниями |
| Треков нет | Трек как сущность уровня проекта |
| Вехи только у проекта | Плюс вехи по контрагенту (график интеграций) |
| Отчётов нет | Замораживаемый снимок отчёта за период |
| Внешних исполнителей нет | Внешний ответственный у задачи |
| Упор на импорт из Excel | Excel — источник разовой миграции и постоянных выгрузок; производственный трек связан с Jira |
