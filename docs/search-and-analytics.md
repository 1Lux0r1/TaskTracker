# Поиск, фильтрация, календарь и аналитика

Четыре темы, которые опираются на одну и ту же модель данных и поэтому описаны
вместе. Всё, что здесь заявлено, проверено на PostgreSQL 16 — где есть
ограничение, оно названо.

## 1. Поиск по письмам

Письмо ищут двумя способами, и они принципиально разные.

### 1.1. По номеру

Номер выглядит как `64-01-16906/26`. Человек помнит его частями: вводит
`16906`, или `16906/26`, или переписывает из другого документа слитно.
Поэтому хранятся две формы: исходный номер и `numberDigits` — только цифры,
генерируемая колонка. Обе покрыты триграммными индексами, поэтому поиск по
фрагменту идёт по индексу, а не перебором.

Проверено: `16906` находит письмо; `64011673926` находит `64-01-16739/26`.

### 1.2. По ключевым словам

Здесь два слоя, и второй существует не для красоты.

**Слой первый — полнотекстовый поиск** с русской конфигурацией. Словоформы
одного слова сводятся к общей основе: запрос «согласования» находит и
«Согласование проекта ТЗ», и «О согласовании материалов». Тема письма весит
больше комментария, поэтому совпадение в теме поднимается выше в выдаче.

**Границы этого слоя проверены на живой базе:**

- Стеммер не связывает части речи. «Согласовать» даёт основу `согласова`, а
  «согласование» — `согласован`, и одно другое не находит.
- Составное слово — один токен. «Геотрест» не найдёт «Мосгоргеотрест».

Обе ситуации для этих данных обычны: названия организаций часто составные, а
искать начинают с полуслова.

**Слой второй — поиск по фрагменту** триграммными индексами по приведённому к
нижнему регистру тексту. Он закрывает ровно то, где первый бессилен.
Проверено: «геотрест» находит «Мосгоргеотрест».

Пользователь про эти слои не знает: он вводит одну строку. Запрос объединяет
оба слоя и поиск по номеру, а результаты ранжируются — сначала совпадение по
номеру, затем по теме, затем по тексту заметок.

### 1.3. Поиск по хронике

Заметки индексируются отдельно: генерируемая колонка не может читать другую
таблицу, поэтому текст заметок не попадает в индекс письма. Запрос ищет по
обоим индексам и объединяет результат. Для пользователя это одно поле поиска.

Это важно на практике: в исходных таблицах половина смысла лежит именно в
хронике, и поиск, который её не видит, бесполезен.

### 1.4. Переносимость на SQLite

Описанное выше — средства PostgreSQL. Если базой станет SQLite, поиск делается
иначе, но разрыв меньше, чем кажется. Проверено на SQLite 3.45.1; токенизатор
`trigram` требует SQLite 3.34 или новее, так что на любой актуальной версии
выводы ниже верны:

| Возможность | PostgreSQL | SQLite |
| --- | --- | --- |
| Фрагмент номера | триграммный индекс | FTS5 с токенизатором `trigram`: `LIKE '%16906%'` идёт **по индексу** |
| Фрагмент внутри слова | триграммный индекс | тот же токенизатор: `LIKE '%геотрест%'` находит «Мосгоргеотрест» |
| Словоформы | стеммер `russian` | префиксный запрос `согласов*` находит и «Согласование», и «согласовании» |
| Ранжирование выдачи | `ts_rank` с весами полей | `bm25()` в FTS5, веса задаются, но настраивается грубее |
| Календарь, опора аналитики | представления | представления есть, синтаксис почти тот же |

Что в SQLite действительно отсутствует — русский стеммер: `porter` в FTS5
только английский. Но выигрыш от него скромнее, чем ожидаешь: стеммер
PostgreSQL тоже не связывает части речи («согласовать» и «согласование» дают
разные основы), а обычные словоформы одного слова покрываются префиксным
запросом.

Честный вывод: на этих данных поиск на SQLite получится почти таким же.
Отличия — более грубое ранжирование и необходимость строить префикс из
пользовательского ввода вместо готовой морфологии. Выбор базы данных стоит
делать по другим основаниям (одновременный доступ, резервное копирование,
требования к юридически значимым данным), а не по поиску.

## 2. Умная фильтрация

Фильтрация состоит из трёх слоёв.

### 2.1. Быстрые фильтры

Предустановленные, всегда под рукой, отвечают на вопросы, которые задают
каждый день:

- **Просрочено** — срок прошёл, статус не закрыт.
- **Горит на этой неделе** — срок в пределах семи дней.
- **Ждёт нас** — входящее письмо без ответа, документ, где наша сторона не
  подписала.
- **Ждёт их** — исходящее без ответа, документ, где не подписала сторона
  контрагента. Разделение «ждёт нас» и «ждёт их» — главный вопрос на любом
  статусе, и в таблице на него ответить нельзя.
- **Без ответственного** — строка, за которую никто не взялся.

Просрочка нигде не хранится полем: она считается запросом от текущей даты. В
исходной таблице она записана текстом и устаревает в тот же день.

### 2.2. Фильтр по полям

Контрагент, трек, статус, ответственный, диапазон дат, направление письма,
вид документа, статус конкретной стороны подписания. Условия соединяются И/ИЛИ.

Фильтр по контрагенту работает через справочник с вариантами написания:
выбрав организацию, пользователь получает все её письма независимо от того,
как её записали в исходном файле.

### 2.3. Сохранённые фильтры

Собранный набор условий сохраняется под именем — личный или общий на всю
команду, с возможностью закрепить в боковой панели. Хранится деревом условий
в JSONB.

Решение по безопасности: поля и операторы проверяются схемой на сервере.
Сохранённый фильтр — это структура данных, а не кусок запроса, и превратить
его в произвольный SQL нельзя.

## 3. Календарь

Календарь показывает в одной сетке все даты проекта: сроки исполнения писем,
сроки и плановые даты задач, вехи проекта, этапы интеграции по контрагентам,
сроки интеграции по документам и границы отчётных периодов.

**Решение: отдельной таблицы событий нет.** Календарь — представление
(`calendar_event`), собирающее даты из сущностей, которым они принадлежат.
Причина: дублировать дату в таблицу событий значит держать две правды и
синхронизировать их при каждом изменении. Представление читается одним
запросом с фильтром по диапазону.

Каждое событие несёт признак `is_open` — просрочено ли оно и требует ли
внимания. Закрытые письма и достигнутые вехи в календаре остаются, но не
подсвечиваются.

### Производственный календарь

Отдельный справочник нерабочих дней, включая переносы (рабочая суббота).
Нужен потому, что сроки официальной переписки исчисляются в рабочих днях, и
без него срок «десять рабочих дней» считается неверно.

Проверено: расчёт рабочих дней между датами с учётом справочника работает.

## 4. Аналитика

### 4.1. Текущие значения — запросом

Объёмы небольшие (десятки строк), поэтому никакого OLAP, витрин и отдельного
хранилища. Всё считается запросом по живым данным:

- Переписка: сколько в работе, сколько просрочено, среднее время ответа,
  разрез по контрагентам.
- Документы: воронка подписания по стадиям, на какой стороне стоит документ,
  сколько отказов и по каким причинам.
- Задачи: выполнено за период, просрочено, распределение по трекам и людям.
- Интеграции: сколько контрагентов прошло каждый этап.

Для документов есть готовая опора — представление `document_signing_state`:
по каждому документу число сторон, сколько подписали, сколько отказали,
сколько ждём, даты первой отправки и последнего подписания. Из него считаются
и воронка, и ответ на вопрос «где документ стоит».

### 4.2. Динамика — снимками

Для графиков «как менялось со временем» есть `MetricSnapshot`: суточный срез
значения метрики с разрезом. Заполняется фоновой задачей раз в сутки.

Причина, по которой это отдельная таблица, а не расчёт по журналу изменений:
восстановить «сколько было просрочено месяц назад» по журналу дороже и менее
надёжно, чем записать значение в тот день. Журнал отвечает на вопрос «кто и
что поменял», а не «каким было состояние».

### 4.3. Чего в аналитике сознательно нет

- Конструктора дашбордов. Панели предустановлены в коде; конструктор при трёх
  пользователях не окупается.
- Прогнозов и трендовых моделей. На пятидесяти письмах любая экстраполяция
  будет выдумкой.
- Выгрузки в BI-систему. Появится, если аналитика перерастёт встроенные
  панели.

## 5. Приложение: SQL представлений для справки

Схема и миграции из этой ветки в основную кодовую базу не переносятся — за
основу взято приложение из ветки `claude/project-thread-74ojym`. Но логика двух
представлений от выбора базы не зависит, поэтому сохранена здесь. Это справка,
а не миграция.

### calendar_event — все даты проекта в одной выборке

Собирает шесть источников дат. Признак `is_open` показывает, требует ли событие
внимания: незакрытое письмо, невыполненная задача, недостигнутая веха.

```sql
CREATE VIEW calendar_event AS
  SELECT 'letter_due' AS kind, l.id AS entity_id, l."projectId" AS project_id,
         l."dueDate" AS event_date, 'Срок исполнения: ' || l.number AS title,
         l."counterpartyId" AS counterparty_id,
         (l.status NOT IN ('ANSWERED','SIGNED','NOTED','CLOSED_NO_ACTION')) AS is_open
  FROM "Letter" l WHERE l."dueDate" IS NOT NULL

  UNION ALL
  SELECT 'task_due', t.id, t."projectId", t."dueDate", t.title, t."counterpartyId",
         (s.category NOT IN ('DONE','CANCELLED'))
  FROM "Task" t JOIN "ProjectStatus" s ON s.id = t."statusId"
  WHERE t."dueDate" IS NOT NULL AND t."deletedAt" IS NULL

  UNION ALL
  SELECT 'milestone', m.id, m."projectId", m."dueDate", m.name, NULL,
         (m."reachedAt" IS NULL)
  FROM "Milestone" m

  UNION ALL
  SELECT 'integration_stage', cm.id, cm."projectId", cm."plannedDate", cm.stage,
         cm."counterpartyId", (cm."actualDate" IS NULL)
  FROM "CounterpartyMilestone" cm WHERE cm."plannedDate" IS NOT NULL;
  -- плюс плановые даты задач, сроки интеграции документов и границы
  -- отчётных периодов тем же приёмом
```

### document_signing_state — состояние подписания по сторонам

Опора и для воронки подписания, и для ответа «на какой стороне документ
стоит».

```sql
CREATE VIEW document_signing_state AS
  SELECT d.id AS document_id, d."projectId" AS project_id, d.kind,
         d."counterpartyId" AS counterparty_id,
         count(p.id) AS parties_total,
         count(p.id) FILTER (WHERE p.status = 'SIGNED')  AS parties_signed,
         count(p.id) FILTER (WHERE p.status = 'REFUSED') AS parties_refused,
         count(p.id) FILTER (WHERE p.status IN ('NOT_SENT','SENT','UNDER_REVIEW','AGREED'))
           AS parties_pending,
         min(p."sentAt") FILTER (WHERE p.status <> 'NOT_SENT') AS first_sent_at,
         max(p."signedAt") AS last_signed_at
  FROM "Document" d
  LEFT JOIN "DocumentParty" p ON p."documentId" = d.id
  GROUP BY d.id, d."projectId", d.kind, d."counterpartyId";
```

В SQLite `FILTER` не поддерживается — заменяется на
`sum(CASE WHEN … THEN 1 ELSE 0 END)`, остальное переносится дословно.

### Порядок расчёта состояния документа

Не забыть при переносе: явный исход перебивает вывод из сторон.

```
если stateOverride задан        -> он и есть состояние
иначе если есть отказ           -> REJECTED
иначе если подписали все        -> SIGNED
иначе если подписал кто-то      -> PARTIALLY_SIGNED
иначе                           -> DRAFT
```

Перебор нужен потому, что в реестре «ДС к NDA» сторон по колонкам нет, а отказ
записан только итоговой формулировкой.
