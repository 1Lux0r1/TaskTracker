# Модуль «Планирование развития»

Перенос методики из книги «Планирование развития системы» в систему. MVP:
ввод руками, «умный» только генератор шифра. Раздел в меню — «Планирование
развития», адрес `/planning`.

## Уровни и сущности

Система → Направление → Блок (направление + часть) → ДК → задачи плана.
В словах книги заказчика: направление ОФТ (TATep) → раздел ОФТ (TATep.1) →
пункт дорожной карты (TATep.1.1) → задачи «Плана работ» по МС.

| Сущность | Таблица | Ключ уникальности |
|---|---|---|
| Система | `PlanSystem` | код (RKII) |
| Направление | `PlanDirection` | система + код |
| Часть направления (= блок) | `PlanDirectionPart` | направление + код |
| Подсистема | `PlanSubsystem` | система + код |
| МС | `PlanModule` | система + номер реестра; подсистема + номер в подсистеме |
| Этап | `PlanStage` | код |
| ДК | `PlanDk` | часть + номер |
| Задача плана | `PlanTask` | шифр |

Блок отдельной таблицы не имеет: это часть направления. Статусы ДК, приоритеты
направлений и уровни этапов — в `src/lib/domain.ts`.

## Шифр

Действующий формат — формат книги планирования (с 24.10.2026):
`СИСТЕМА.НАПРАВЛЕНИЕ.РАЗДЕЛ.ПУНКТ.ПОДСИСТЕМА.МС.ЭТАП`, например
`RKII.TATep.1.1.TA.1.Р`. Подсистема — та, где живёт МС, номер МС — внутри
подсистемы (TA.1), номера без ведущих нулей. Задача пункта без МС (ОА, БА,
Арх) — без подсистемы: `RKII.TATep.1.1.БА`. Неизвестные позиции опускаются,
номер повтора дописывается к этапу только у повторов (Р, Р2, Р3).

Собирает шифр только `src/lib/planning/cipher.ts`, формат задаёт
`CIPHER_SETTINGS`:

- `segments` — порядок сегментов;
- `subsystemSource` — откуда подсистема: из МС (`"ms"`) или из ДК (`"dk"`);
- `msNumber` — номер МС в шифре: внутри подсистемы или сквозной по реестру;
- `numberWidth` — знаков у номеров: 1 (без нулей) или 2 (01).

Формат первого ТЗ (`…ЧАСТЬ.ПОДСИСТЕМА.ДК.МС.ЭТАП`, RKII.Gaz.Rte.TA.01.08.Р)
сохранён как `CIPHER_SETTINGS_TZ`.

Шифр хранится у задачи (уникальный индекс, поиск «содержит»). После смены
формата или кода в справочнике шифры пересобираются: при правке справочника
автоматически, после смены настройки — кнопкой «Пересобрать шифры» на
вкладке «Справочники».

У МС два номера, оба из счётчиков и оба не переиспользуются: номер реестра
(`PlanSystem.lastMsNumber`, сквозной, в шифр не входит) и номер в подсистеме
(`PlanSubsystem.lastMsNumber`, входит в шифр). При переносе МС в другую
подсистему он получает там следующий номер. Номер ДК — следующий в блоке.

## Сроки

Старт, длительность в неделях, финиш: достаточно двух, третье считается
(`src/lib/planning/dates.ts`). Финиш — последний день включительно, не раньше
старта. Календарь 2025–2029 (`PLAN_CALENDAR`): книга ведёт план с апреля
2025-го, сроки дорожной карты доходят до 2029-го.

## План работ за период и выгрузка в Excel

На вкладке «План работ» под кнопкой «Фильтры» — период и шкала: текущий
квартал, полугодие, год (по умолчанию), весь план или свой период по месяцам;
шкала по неделям (ISO, с понедельника) или по месяцам. Кнопка «Выгрузить в
Excel» отдаёт ровно то, что на экране, — тот же период, шкалу и поиск
(`/api/export?entity=plan&…`, `src/lib/planning/export.ts`).

В файле лист «План работ» в раскладке книги: Код Бизнес (пункт), Код МС с
этапом, шифр, наименование, статус и срок пункта, старт, финиш, недели, затем
колонки периода с закрашенными клетками (по пункту — фиолетовый, по МС —
синий, повтор — красный, срок пункта по задачам — голубой). Лист
«Параметры» — система, период, поиск, кто и когда выгрузил, легенда. В
выгрузку попадает задача, задевающая период хотя бы днём, и задачи без сроков.

## Команды

```
npm run planning:sample                         # тестовый пример: Gaz · Rte · ДК 1 и 2, МС TA.3
npm run planning:import -- книга.xlsx           # пробный прогон, база не меняется
npm run planning:import -- книга.xlsx --apply   # запись книги в базу
```

Импорт читает книгу «Планирование_развития_системы_структура»: на листе
«Справочник» — подсистемы, этапы, реестр МС и направления (области вроде TA —
группа направлений, в модуль не грузятся); «ОФТ» — разделы; «Дорожная карта»
— пункты со статусом, сроком и ответственным; «План работ» — задачи. Таблицы
находятся по подписям колонок, ссылки вида `='Дорожная карта'!B85` и `=$B6`
разворачиваются сами (книга сохранена без вычисленных значений), сроки задачи
берутся из закрашенных месяцев шкалы, без закраски — месяц колонки «Срок».

Пробный прогон проходит всю запись в транзакции и откатывает её, поэтому его
замечания те же, что будут при записи. Строки, которые не сходятся (пункта нет
в карте, МС нет в реестре, неизвестный этап, код не по правилу, дубль шифра),
пропускаются и перечисляются; годные пишутся. Записи находятся по коду и
номеру, задачи — по шифру: повторная загрузка обновляет, а не дублирует.

Что в книге есть, а в модуль не грузится: статусы задач «Плана работ»,
приоритет, статус и срок разделов ОФТ, области направлений, лист «Сверка с
картой». Статус пункта книги переводится в статус ДК: «Выполнено» → завершено,
«В работе», «Разработка», «Тестирование» → производство, «Анализ» → анализ,
«Заморожено» → заморожено, «В очереди» и пусто → предпроектное исследование.

## Миграция и откат

Миграция `20261013203439_planning_module` только добавляет восемь таблиц,
существующие не меняет. `20261024090000_planning_book` добавляет номер МС в
подсистеме, счётчик подсистемы и срок ДК; уже заведённые МС нумеруются внутри
подсистемы по порядку реестра. Откат — в обратном порядке:

```
npx prisma db execute --file prisma/migrations/20261024090000_planning_book/down.sql
npx prisma db execute --file prisma/migrations/20261013203439_planning_module/down.sql
```

Каждый скрипт удаляет своё (колонки или таблицы модуля) и снимает отметку о
применении миграции, поэтому `npm run db:deploy` после отката накатит заново.

Перед откатом остановите приложение и сделайте копию базы (`npm run backup`):
откат удаляет данные модуля.

## Чего в MVP нет

Модуль «Контроль» (узкие места, нагрузка, конфликты по МС), связь с Jira,
карточки и статусы задач плана, автоматические переходы статусов,
автогенерация наименований, корзина, отдельные роли доступа.
