# TaskTracker — общий контекст для всех агентов

Этот файл читает каждая сессия, открывшая репозиторий. Он заменяет чтение чужих
веток: всё, что нужно, чтобы включиться в работу, собрано здесь. Общение с
заказчиком и все документы — **по-русски**.

Правило файла: здесь только то, что не выводится из кода и не живёт в `README.md`
и `docs/`. Технику смотри там, решения заказчика и распределение работы — здесь.
Если что-то из файла устарело, правит аналитик (ветка «Бизнес-анализ и
требования»), а не тот, кто первым заметил.

## 1. Что это за система

TaskTracker — веб-приложение для ведения проекта **со стороны заказчика**.
Заказчик — Lux0r (GitHub `1Lux0r1`), ведёт проект АИС РКИИЭ со стороны ДИТ Москвы.
Сейчас проект живёт в Jira (разработка) и в Excel (всё остальное). Уходим от
Excel, Jira остаётся для разработки.

Что задаёт всю архитектуру:

- **Задача и документ — два равноправных объекта учёта.** Юридический трек
  (письма ЭДО, регламенты, NDA, допсоглашения) — половина системы, а не придаток.
- **Подписание документа — матрица сторон** (ДИТ, РСО, ДЖКХ и другие): у каждой
  стороны свой статус, итоговый статус документа **вычисляется** из них и руками
  не вводится. Отказ стороны — штатный исход, он блокирует документ.
- **Письма ЭДО вносятся руками.** Интеграции с МосЭДО не будет: ссылка на карточку
  вставляется вручную. Значит, форма заведения письма должна быть рассчитана на
  серийный ввод.
- **Отчёт руководству — объект системы, а не файл:** черновик собирается из данных,
  человек правит, отправленная версия замораживается.
- **Связь с Jira — поле со ссылкой**, двусторонней синхронизации нет (лежит в бэклоге).
- **Пилот:** один проект, три человека, дальше масштабирование до ~50.

### Пользователи и роли

Две роли: **администратор** и **участник**. Права на данные одинаковые — полный
CRUD у всех троих. Отличий два: администратор заводит сотрудников, пароли и
доступы; публичное отображение записи меняет тоже он, а участник задаёт видимость
только в момент заведения записи. Первый администратор создаётся командой при
установке (`npm run auth:admin`). Внешнего доступа у системы нет, учёт внутренний.

Контрагенты (ДИТ, РСО, ДЖКХ, Россети и прочие) — **справочник адресатов писем и
сторон подписания, а не пользователи системы**. Это подтверждено заказчиком
дословно: «организации остаются, но они не будут пользователями системы». Фраза
«контрагентов не будет» в более раннем разговоре означала отсутствие внешнего
доступа, а не удаление их из модели. Ничего из модели не удаляем.

### Сущности и их жизнь

- **Проект** — код, название, сроки, руководитель; архивация вместо удаления.
- **Трек** — справочник проекта. Треки заводит сама команда: четыре трека из Excel
  созданы при установке, их переименовывают, красят, двигают, добавляют свои.
  Трек с задачами не удаляется, а уходит в архив. Трек задачи всегда из её проекта —
  это проверяется на сервере.
- **Задача** — трек, ответственный (внутренний и внешний), сроки, статус,
  приоритет, готовность, подзадачи, письмо-основание, вложения, лента хроники.
  Статусы: Новая · Бэклог · К выполнению · В работе · На проверке · Готово ·
  Отменена. **Заведённая задача всегда получает статус «Новая»**, в форме создания
  статус не спрашивают.
- **Артефакт задачи** — чем работа подтверждается. Видов пять: ссылка на ЭДО,
  ссылка на Jira, документ системы, своя ссылка, своё значение. Артефактов у задачи
  может быть несколько. Слова «результат» в интерфейсе больше нет.
- **Письмо ЭДО** — направление, номер, дата, тема, контрагент, ссылка на ЭДО, срок,
  статус; у входящего резолюция, у исходящего подписант и письмо-основание. Дубль
  определяется парой «номер + дата». Ответ связан с исходным письмом, и связь
  должна быть видна с обеих сторон.
- **Документ** — вид, контрагент, срок, стороны подписания, итоговый статус.
- **Встреча** — повестка, материалы, решения, правка после встречи (в работе).
- **Отчёт руководству** — период, блоки, заморозка при отправке (в бэклоге по
  настраиваемому шаблону).
- **Лента записей (хроника)** — у задачи, письма и документа: дата события отдельно
  от даты внесения.

### Ловушки предметной области

Всё это выведено из разбора реального файла заказчика, а не из предположений.
Не «исправляйте» их обратно:

1. Колонка «Статус» в его реестрах задач — **не статус, а хроника с датами**
   («05.05.2026 драфт загружен в ЭДО / 06.05.2026 на согласовании у Ежовой»).
   Поэтому в системе лента записей, а не одно поле.
2. Одна организация записана до четырёх раз по-разному — отсюда справочник
   контрагентов с псевдонимами.
3. Просрочка в файле записана текстом («просрочка 49 дн.») и устаревает в тот же
   день — считаем её на лету.
4. Своя сторона подписания отмечается флагом `isInternal` в справочнике
   контрагентов, а не выводится из отсутствия связи.
5. `Task.externalKey` — ключ строки **импорта** (в файле заказчика это «1», «2»,
   «3»). Ключ задачи во внешнем трекере — отдельное поле `externalTaskKey`.
   Не путать их.
6. SQLite не понижает регистр кириллицы, поэтому поиск живёт в `searchIndex`.
   Если данные попали в базу мимо приложения — выполнить `npm run search:reindex`,
   иначе русский поиск молча пуст.

Подробный разбор файла заказчика: `docs/excel-analysis.md`, сопоставление колонок —
`docs/import-mapping.md`.

## 2. Правила заказчика

Их нарушение — переделка, а не замечание.

- **Только русский язык** в ответах, документах, коде-комментариях и интерфейсе.
- **Excel — источник сведений о том, какая информация ведётся, а не образец экрана.**
  Первая версия макетов была забракована целиком: «ты сделал всё в формате таблиц».
  Экраны-таблицы не принимаются: карточки, ленты, доски, визуальные состояния,
  поярче. Никаких сеток с рамками ячеек, колонок «№», строк итогов.
- **Приложенный файл — всегда источник сведений, а не макет.** На этом же обожглись
  второй раз с разделом «План работы» (см. ниже).
- **PR в `main` открывается и мержится только по слову Lux0r.** Сам по себе PR не
  открывается никогда.
- **Не разворачивать, не покупать, не отправлять ничего наружу** без его слова.
- Пишет он между делами и читает по диагонали: ответ ведёт с ответа или с решения,
  которое нужно принять; вопрос — такой, на который можно ответить одним словом,
  с короткой строкой на вариант и помеченной рекомендацией.
- Не отчитываться о каждом шаге: ход работы живёт в статус-чеклисте ветки, а
  сообщение пишется, когда есть результат, блокер или вопрос к нему.
- При нехватке вводных — разумный дефолт с явным называнием, а не остановка.

### Что уже отвергнуто (не предлагать заново)

- **Табличные экраны** в любом виде.
- **Раздел «План работы»** в первом заходе (дерево работ, сетевой график с
  критическим путём, таймлайн): «Это совсем не то, что я хотел. Убирай из макета и
  заноси задачу в бэклог». Лежит в бэклоге. Перед новым заходом надо спросить, как
  он ведёт график сейчас и что экран должен показывать в первую очередь.
- **Формат Ганта** во вкладке документов — заменён списком с фильтрами
  («Юридический трек»).
- **Настройка дашбордов** — большая работа, ушла в бэклог, но место под вывод
  дашбордов в «Сегодня» заложено.
- **Календарь «разноцветными линиями»** — переработан: месяц, неделя, список,
  панель выбранного дня; полосы длительности остались выключенным по умолчанию
  переключателем.

### Правила интерфейса

- Обращение к пользователю **по имени**, не по фамилии.
- На экране **чётное число блоков** в ряду, иначе сетка разъезжается.
- В реестрах: строка поиска на виду и **одна** кнопка «Фильтры», внутри которой все
  условия. Лишние переключатели на панель не выносить.
- Единый язык блоков на всех экранах; удаление — с отменой в тосте.
- Справочники держат всю справочную информацию по проекту и контрагентам, включая
  реестр ответственных представителей контрагентов.

## 3. Кто чем занят: ветки и их назначение

Работа разложена по веткам проекта. Каждая ветка — отдельная сессия Claude. Ходить
надо к назначенной ветке, а не решать за неё и не изучать её историю.

### Координатор (общий чат проекта)

Держит общий чат, принимает задачи от Lux0r, заводит ветки и следит, чтобы ни одна
не встала. Внутри веток не пишет. К нему — когда нужно завести новую ветку или
передать что-то в общий чат.

### Бизнес-анализ и требования («аналитик»)

**Отвечает за:** требования и их актуальность, счёт минимума функционала, модель
данных на уровне требований, разбор файла заказчика.
**Производит:** документ требований — https://claude.ai/artifact/26gFkzCe7Z5RiU15poRXm2
(вкладка «Требования и бизнес-анализ» — функциональные требования FR, модель данных,
ER-диаграмма, НФТ, бэклог; вкладка «Минимальный функционал» — 39 пунктов с
состоянием). Правит этот файл.
**Не делает:** не пишет код, не рисует макеты, не ведёт бэклог менеджера.
**К нему идут:** за формулировкой требования, за состоянием минимума, при
расхождении кода и требований.

### Интерфейс и переезд из Excel («интерфейс»)

**Отвечает за:** макеты всех экранов и то, как пользователь работает.
**Производит:** макеты — https://claude.ai/artifact/V7PrRrW1DHFAL6CfNqwvRn и их
описание `docs/ui/mvp-screens.md` (ветка `claude/project-thread-o3fxmf`).
**Не делает:** не пишет код и не меняет требования в обход аналитика.
**К нему идут:** за тем, как экран должен выглядеть и вести себя.

### Разработчик

**Отвечает за:** весь код. Работает в ветке `claude/project-thread-74ojym`.
**Производит:** приложение, миграции, тесты, установочные скрипты, `docs/`.
**Не делает:** не решает за аналитика, что входит в требование, и не открывает PR в
`main` без слова Lux0r. Закрытый пункт сообщает менеджеру на проверку.
**К нему идут:** за состоянием кода и за тем, что реально сделано.

### Менеджер проекта

**Отвечает за:** бэклог (https://claude.ai/artifact/6Ap9qorAxTDxREZYvgUQyy),
контроль сделанного, UI-проверки по требованиям аналитика, предложения из лучших
практик.
**Производит:** приёмки и возвраты с дефектами, пополнение бэклога.
**Не делает:** код не пишет; счёт минимума не ведёт — сдвигает его аналитик по его
сообщениям.
**К нему идут:** за тем, что проверено и что возвращено.

### Запуск в работу

**Отвечает за:** всё, что нужно, чтобы система стала рабочей: размещение, установка,
данные, ИБ, резервные копии.
**Не делает:** ничего не разворачивает и не покупает без слова Lux0r.

### Как ветки разговаривают между собой

Межветочная записка пишется, только когда она меняет работу адресата: приёмка,
возврат с дефектом, изменение требования, блокер. Отчёты о шагах не рассылаются.
Счёт минимума и требования меняются в одном месте — у аналитика; все остальные ему
сообщают, а не правят сами.

## 5. Размещение и запуск

Решение Lux0r от 23.09.2026: **на время пилота он разворачивает систему на своём
личном компьютере, потом — российское облако.** Ставит сам. Внешнего доступа нет.

Что из этого следует для кода: установка одним скриптом (Windows по умолчанию,
плюс macOS), доступ коллег по локальной сети по http с `SESSION_COOKIE_SECURE=false`
(без HTTPS вход иначе не работает), автозапуск, ежедневная резервная копия базы
**и каталога вложений** (`ATTACHMENTS_DIR`, по умолчанию `var/attachments`),
Docker + Caddy для облака, инструкция по установке в `docs/`. Комплект обязан запускать
`npm run auth:admin`, иначе в систему некому войти.

## 6. Стек и карта кода

Стек выбран Claude по умолчанию, заказчик его не задавал:

- Next.js 16 App Router + React 19 + TypeScript, серверные экшены вместо отдельного API.
- Prisma 7 поверх SQLite через `@prisma/adapter-better-sqlite3` (Prisma 7 требует
  драйвер-адаптер). Переезд на PostgreSQL описан в `README.md`.
- Tailwind CSS 4 без библиотеки компонентов. Класс, который переиспользуется через
  `@apply` внутри другого класса, объявляется через `@utility`, а не в
  `@layer components`, иначе сборка падает на «unknown utility class».
- ExcelJS для чтения и записи .xlsx, Vitest для тестов, Zod для валидации.

Карта:

- `src/app/` — страницы по разделам; `src/app/actions/` — серверные экшены (вся
  запись данных идёт через них, там же проверки прав и принадлежности проекту).
- `src/components/` — формы и виджеты.
- `src/lib/domain.ts` — **единственный источник правды** по статусам, приоритетам и
  видам артефактов: SQLite не поддерживает enum, значения хранятся строками.
- `src/lib/` — предметные модули: `letters.ts`, `tracks.ts`, `search.ts`,
  `attachments.ts`, `auth.ts`, `reports.ts`, фильтры реестров, `validation.ts`.
- `src/lib/excel/` — импорт и экспорт, разбор хроники и колонок.
- `prisma/schema.prisma` и `prisma/migrations/` — модель и миграции.
- `docs/` — архитектура, модель данных, разбор Excel, сопоставление колонок, поиск и
  аналитика, дорожная карта.

### Команды

```
npm ci                 # чистая установка (postinstall делает prisma generate)
npm run dev            # разработка
npm run build          # сборка
npm test               # тесты (vitest)
npm run typecheck      # tsc --noEmit
npm run lint           # eslint
npm run db:migrate     # миграции в разработке
npm run db:deploy      # миграции + переиндексация поиска
npm run db:seed        # демо-данные
npm run auth:admin     # создать первого администратора
npm run search:reindex # пересобрать поисковый индекс
```

Перед коммитом прогоняются `npm test`, `npm run typecheck`, `npm run lint`.
