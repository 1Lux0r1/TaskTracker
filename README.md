# TaskTracker

Веб-приложение для управления проектами со стороны заказчика: производственный
трек, переписка ЭДО, подписание юридически значимых документов, отчёты
руководству и аналитика. Существующие реестры загружаются из Excel как есть.

## Зачем

Заменить ведение проекта в Excel-таблицах, сохранив привычный вход и выход:
файл можно загрузить как есть, а данные в любой момент выгрузить обратно в .xlsx.
Модель построена на разборе реального рабочего файла: в нём оказалось восемь
разных реестров, а не один список задач.

| В Excel | В TaskTracker |
| --- | --- |
| Лист на проект | Проект с кодом, сроками и руководителем |
| Строка таблицы | Задача со статусом, приоритетом, сроком, исполнителем и треком |
| Реестр переписки отдельным листом | Письма ЭДО как своя сущность с поиском и сроками |
| Колонки «Статус подписания ДИТ / РСО / ДЖКХ» | Стороны подписания: у каждой свой статус, итог считается по ним |
| Колонка «Статус» с хроникой дат | Лента записей, где дата события отдельно от даты внесения |
| Текст «просрочка 49 дн.», устаревающий в тот же день | Просрочка считается при каждом открытии |
| Одна организация в четырёх написаниях | Справочник организаций с вариантами написания |
| Отчёт руководству собирается руками | Черновик собирается из данных и замораживается при отправке |
| Ручная подсветка просрочек | Просроченное считается и подсвечивается автоматически |
| Копия файла у каждого | Одна база, все видят актуальные данные |

## Возможности

- **Сегодня** — стартовый экран. Приветствие по имени (имя для обращения
  человек задаёт себе сам в профиле, иначе берётся из ФИО). Три плитки —
  задачи, письма, встречи: крупная цифра, пилюля «новых», полоса состава и
  строка разбивки; плитка кликабельна целиком. Ниже четыре карточки —
  просрочено, письма без ответа, документы на подписании, ближайшие встречи —
  по три строки и ссылка «Ещё N» в соответствующий реестр с тем же фильтром.
  Экран собирается из одного списка блоков, чтобы настройку дашбордов можно
  было добавить, не переделывая раздел.
- **Проекты** — код, название, описание, статус, сроки, руководитель; по проекту
  считаются готовность и часы (план / факт).
- **Задачи** — трек из справочника проекта,
  статус, приоритет, внутренний и внешний ответственный, даты, оценка и факт в
  часах, процент готовности, подзадачи, письмо-основание, лента хроники.
  Заведённая задача всегда получает статус «Новая»: в форме создания его не
  спрашивают. Чем работа подтверждается — артефакты: карточка в ЭДО, задача во
  внешнем трекере, документ системы, своя ссылка или просто значение; их у
  задачи может быть несколько.
- **Канбан-доска** — колонки по статусам, перенос кнопками (работает без
  JavaScript и на телефоне).
- **Переписка ЭДО** — входящие и исходящие письма, организация, срок исполнения,
  ссылка на карточку в ЭДО, реквизиты ответа, ключ задачи во внешнем трекере.
  Форма заведения подстраивается под направление: у входящего письма резолюция,
  у исходящего подписант и письмо, в ответ на которое оно идёт; подписи полей
  тоже меняются. Отметка «ответ не требуется» снимает срок и принимает письмо
  к сведению. Выборки: «просроченные», «срок в ближайшую неделю», «ждут нашего
  ответа», «ждём их ответа», «без ответственного», «без срока».
- **Юридический трек** — регламенты, ДС к NDA, контракты списком карточек,
  сгруппированным по стадиям: сначала то, что требует действий (отказ,
  возвращён на доработку), в конце законченное (подписан, передан в дело).
  Подписание описывается **матрицей сторон**: у каждой стороны свой статус,
  итог подписания выводится из них, отказ любой стороны блокирует документ.
  Стадии «возвращён на доработку» и «передан в дело» ставит человек, и матрица
  их не перебивает. Выборка «ждём» отвечает, чьей подписи не хватает — нашей
  или внешней стороны (своя организация отмечается в справочнике организаций).
- **График интеграций** — реестр подключения организаций: строка — организация,
  столбец — этап (регламент направлен, регламент подписан, система организации
  готова, интеграция в dev-среде, открытие в тестовой среде). В клетке план,
  факт и примечание; цвет показывает состояние — факт важнее плана, просрочка
  считается от сегодняшнего дня, ближайшая неделя выделена отдельно. Строка
  правится целиком, как её заполняли в Excel: все пять этапов в одной форме.
  Сверху сводка, сколько организаций прошло каждый этап. Организация попадает в
  график пустой строкой и снимается с него с подтверждением; этапы засчитываются
  подряд с начала, перепрыгнуть регламент нельзя.
- **Встречи** — повестка, участники, решения и материалы. Участники берутся из
  сотрудников и справочника представителей организаций, остальных вписывают
  именем. Решение встречи прямо из карточки становится задачей: она попадает в
  реестр задач со статусом «Новая», а на её карточке видно, из какой встречи
  она взялась. Выборки: «предстоящие», «прошедшие», «без решений».
- **Отчёты руководству** — черновик за период собирается из фактических данных
  (закрытое за период, планы, просрочки, отказы в подписании), правится руками
  и замораживается при отправке.
- **Аналитика** — готовность, просрочки, срезы по статусам, трекам, исполнителям,
  направлениям переписки, организациям и статусам документов. Блок «Динамика во
  времени» показывает, как менялись готовность задач и число просрочек за 4, 12
  или 26 недель. Снимков метрик система не ведёт и планировщика у неё нет:
  прошлое считается из самих записей — у задачи есть дата закрытия, у письма
  дата исполнения, и на любую неделю видно, что к ней было закрыто и что уже
  просрочено. Состав работ при этом берётся сегодняшний: в загруженных реестрах
  нет дат заведения строк. График подписания появляется только когда в системе
  есть хотя бы одна дата подписания — у документов из Excel стоит статус, но не
  день.
- **Календарь** — три режима: месяц, неделя и список. Показывает сроки задач,
  писем и документов и дни встреч; просроченное выделено. Типы записей
  включаются переключателями сверху, у каждого счётчик за показанный период.
  В месяце есть переключатель «Показать длительность задач»: задача с датой
  постановки и сроком рисуется полосой цветом своего трека, по умолчанию
  полосы выключены. Панель выбранного дня показывает, что на него приходится,
  и заводит на этот день задачу, встречу или письмо — дата в форме уже
  подставлена.
- **Вход и роли** — вход по рабочей почте и паролю, сессия на 14 дней в
  httpOnly-cookie (в базе только хеш токена). Две роли: администратор ведёт
  пользователей, пароли и доступы, участник работает с данными. Права на
  задачи, письма и документы у ролей одинаковые.
- **Уведомления** — колокол в шапке со счётчиком непрочитанного и экран
  «Уведомления». Четыре повода: задачу назначили на вас, перенесли срок,
  запись просрочена, запись без движения дольше двух недель (`STALE_DAYS` в
  `src/lib/notifications.ts`). Почтового сервера у системы нет, поэтому
  уведомления живут внутри неё. Просрочка и застой видны только по времени, а
  планировщика нет: их пересобирает первый же запрос страницы, но не чаще
  раза в минуту, поэтому колокол показывает свежую картину и без захода в
  раздел. Ключ события не даёт строкам задвоиться. Движение по записи — это
  не только правка карточки: запись в хронике и вложение тоже двигают дату
  правки, иначе задача со свежей записью считалась бы стоящей. Раздел —
  лента событий, и строка из неё не исчезает; счётчик на колоколе, наоборот,
  показывает только то, что горит сейчас, поэтому снятая просрочка из него
  уходит, а строка остаётся. Адресат — ответственный за запись, если его нет
  — владелец проекта, если и его нет — администраторы; о собственном
  действии человек уведомления не получает.
- **Видимость записей** — у задачи, письма и документа есть признак публичного
  отображения. Публичная запись попадает в черновик отчёта руководству,
  служебная остаётся внутри системы и помечена в реестре. Признак задаёт автор
  при заведении: по умолчанию задачи и документы публичные, письма служебные —
  в переписке реквизиты и ФИО, которые наружу не нужны. После создания
  видимость меняет только администратор: участнику поля в форме не показывают,
  а присланное в обход формы значение сервер не применяет. Каждая смена
  попадает в журнал видимости (`/visibility-log`, ссылка со страницы
  «Сотрудники»): видно, кто и когда вывел запись в отчёт или убрал её оттуда.
  В выгрузках Excel видимость идёт отдельной колонкой.
  Видимость задаётся и сразу пачке: в форме импорта — одна пометка на новые
  записи загрузки (у уже заведённых видимость остаётся прежней, пока
  администратор не отметит «Применить и к записям, которые уже заведены»), а в
  реестрах задач, переписки и юридического трека администратор отмечает
  несколько записей — или все показанные одной галочкой — и переключает их
  одной кнопкой. Каждая запись
  уходит в журнал отдельной строкой, а записи, у которых видимость уже нужная,
  не трогаются — иначе журнал заполнили бы смены, которых не было.
- **Вложения** — файлы рядом с задачей, письмом, документом и встречей:
  перетаскиванием
  или выбором, до 20 МБ (предел задан в `src/lib/limits.ts`, оттуда же его
  берут пределы тела запроса в `next.config.ts` — расходиться им нельзя).
  Имена файлов на русском доходят целыми и при загрузке, и при скачивании.
  Файлы лежат в каталоге `ATTACHMENTS_DIR` (по умолчанию `var/attachments`),
  в базе только карточка файла; скачивание закрыто входом, как и остальные
  данные.
- **Треки работ** — справочник проекта: четыре трека из Excel заведены сразу,
  команда переименовывает их, красит, меняет порядок и добавляет свои. Трек с
  задачами не удаляется, а уходит в архив. Свой трек из файла импорта заводится
  в справочник автоматически.
- **Справочники** — отдельный раздел, в нём вся справочная информация системы:
  сотрудники, организации с вариантами написания, ответственные представители
  организаций, треки работ, страницы справочной информации (архитектура
  системы, паспорт проекта, матрица подписания, порядок работы) и страница
  «Виды и статусы» с расшифровкой каждого статуса, вида и стадии. Справочник
  организаций служебный: он нужен, чтобы разные написания одной организации не
  двоились. Организации и их представители пользователями системы не являются,
  учёт внутренний; представитель уходит в архив, а не удаляется, потому что
  отмечен участником прошедших встреч.
- **Импорт из Excel** — три вида реестров: задачи, переписка ЭДО и реестры
  подписания. Лист выбирается вручную или определяется автоматически, шапка
  ищется в первых 10 строках, колонки распознаются по синонимам, строки итогов
  пропускаются. Колонка «Статус» с хроникой дат разбирается в ленту записей.
  Повторная загрузка обновляет записи, а не дублирует их.
- **Экспорт в Excel** — задачи, переписка, документы (двумя листами: документы и
  стороны подписания) и отчёт руководству, плюс файл-образец для импорта.

### Поиск и фильтры

В реестрах задач, переписки, юридических документов и встреч поисковая строка стоит на
виду, а остальные условия собраны под одной кнопкой «Фильтры» с числом заданных
условий. Поиск требует, чтобы встретились все слова запроса; у задач понимает
номер («#12»).

Заданный отбор можно назвать и сохранить: список наборов живёт сверху той же
панели, набор применяется одной ссылкой, переименовывается и удаляется с
подтверждением. Один набор на реестр можно пометить «применять при открытии» —
тогда реестр открывается сразу с ним, а рядом с поиском видно, какой набор
применён, и он снимается одной ссылкой. Наборы личные: у каждого свой срез
работы.

SQLite не приводит кириллицу к нижнему регистру, поэтому поисковая строка
готовится при записи и хранится в поле `searchIndex`. После переноса данных
напрямую в базу её надо пересобрать: `npm run search:reindex` — команда входит
в `npm run db:deploy`.

## Стек

| Слой | Решение | Почему |
| --- | --- | --- |
| Приложение | Next.js 16 (App Router), React 19, TypeScript | один проект на фронт и бэк, серверные экшены вместо отдельного API |
| Оформление | Tailwind CSS 4 | без отдельной библиотеки компонентов и лишних зависимостей |
| База данных | SQLite через Prisma 7 | запускается без внешнего сервера; переезд на Postgres — смена провайдера и адаптера |
| Excel | ExcelJS | чтение и запись .xlsx на сервере |
| Тесты | Vitest | разбор Excel покрыт юнит-тестами |

## Запуск

```bash
npm install               # нужен Node 22 или новее; клиент Prisma создаётся сам
cp .env.example .env      # при необходимости поменяйте путь к базе
npm run db:deploy         # применить миграции и пересобрать поиск
npm run db:seed           # демо-данные: 2 проекта, 7 задач, 4 сотрудника
npm run auth:admin        # первый администратор: спросит почту, ФИО и пароль
npm run dev               # http://localhost:3000
```

Без администратора войти некуда: страница входа сама подскажет, какую команду
запустить. Дальше администратор заводит остальных на странице «Сотрудники».

**Размещение.** Cookie входа помечена флагом Secure, поэтому в продакшене вход
работает только по HTTPS: по обычному http браузер такую cookie отбрасывает и
войти нельзя. Если система ставится во внутренней сети без сертификата,
поставьте в `.env` строку `SESSION_COOKIE_SECURE=false`. По возможности
выбирайте HTTPS: без него по сети открыто идут и пароли.

## Переход на PostgreSQL

1. В `prisma/schema.prisma` заменить `provider = "sqlite"` на `"postgresql"`.
2. `npm i @prisma/adapter-pg` и заменить адаптер в `src/lib/db.ts` на `PrismaPg`.
3. Указать строку подключения в `DATABASE_URL` и выполнить `npm run db:deploy`.

## Что не сделано

Нет: интеграции с ЭДО и Jira (данные заводятся вручную или импортом),
уведомлений о приближении сроков, встреч, диаграммы
Ганта и графика интеграций по организациям (сущность в модели есть, экрана нет),
настраиваемого отчёта руководству и раздела «План работы».

Вход и роли сделаны: без пароля не открывается ни один раздел и не отдаётся
выгрузка. Разграничение внутри данных не вводилось намеренно — на пилоте
проект ведут трое с полным доступом, администратор отличается только правом
вести пользователей.


## Разбор реального файла

Импорт проверен на рабочем файле заказчика — восемь листов, около сотни
содержательных строк (в реестре переписки больше тысячи строк с остатками
форматирования, реальных записей 50).
Что он даёт на нём сейчас:

| Лист | Распознаётся как | Результат |
| --- | --- | --- |
| Письма ЭДО | переписка | 50 строк → 41 письмо (дубли по номеру и направлению схлопнуты), 15 написаний организаций |
| Внутренние задачи | задачи | 20 строк → 16 задач и 8 записей хроники с датами |
| Внешние задачи | задачи | распознаются, включая колонку внешнего ответственного |
| Задачи Производственные | задачи | распознаются |
| Регламенты инф. взаимодействия | реестр подписания | 9 документов, стороны ДИТ / РСО / ДЖКХ |
| ДС к NDA | реестр подписания | 9 документов, стороны «организация» и ДИТ, 2 отказа распознаны |
| РКИИЭ Отчёт АЮ | — | это форма отчёта, а не реестр: заводится в разделе «Отчёты» |
| График интеграций с РСО | — | матрица «организация × этап», в модели есть, экрана пока нет |

Сам файл в репозиторий не кладётся: в нём служебная переписка и персональные
данные, `.gitignore` закрывает `*.xlsx`.
